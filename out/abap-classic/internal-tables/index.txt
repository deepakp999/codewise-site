</div><h2 id="why-internal-tables-matter">Why Internal Tables Matter</h2>
<p>If you learn one thing from this course, make it internal tables. Every ABAP program uses them. Every SAP database query returns data into them. Every ALV report displays them. Every interface passes data through them.</p>
<p>An internal table is ABAP's in-memory data structure for holding multiple rows of data — like a Python list of dictionaries, or a Java ArrayList of objects. But internal tables have unique features that don't exist in other languages.</p>

<h2 id="three-table-types">Three Table Types</h2>
<p>ABAP has three internal table types, each optimized for different access patterns:</p>
<h3 id="standard-table-default">STANDARD TABLE (default)</h3>
<pre class="shiki shiki-themes github-light one-dark-pro" style="--shiki-light:#24292e;--shiki-dark:#abb2bf;--shiki-light-bg:#fff;--shiki-dark-bg:#282c34" tabindex="0"><code><span class="line"><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD">DATA</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">: lt_standard</span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD"> TYPE STANDARD TABLE OF</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> ty_employee</span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD"> WITH</span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD"> EMPTY KEY</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">.</span></span></code></pre>
<ul>
<li>Rows stored in insertion order</li>
<li>Access by index: fast (<code>sy-tabix</code>)</li>
<li>Access by key: slow (linear scan)</li>
<li><strong>Think of it as:</strong> Python's <code>list</code> — append at end, loop through, access by position</li>
<li><strong>Use when:</strong> you fill once and loop through, or access by row number</li>
</ul>
<h3 id="sorted-table">SORTED TABLE</h3>
<pre class="shiki shiki-themes github-light one-dark-pro" style="--shiki-light:#24292e;--shiki-dark:#abb2bf;--shiki-light-bg:#fff;--shiki-dark-bg:#282c34" tabindex="0"><code><span class="line"><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD">DATA</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">: lt_sorted</span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD"> TYPE SORTED TABLE OF</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> ty_employee</span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD"> WITH UNIQUE KEY</span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD"> name</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">.</span></span></code></pre>
<ul>
<li>Rows automatically sorted by the specified key</li>
<li>Access by key: fast (binary search)</li>
<li>Cannot APPEND — must use INSERT (maintains sort order)</li>
<li><strong>Think of it as:</strong> a list that's always sorted — like Python's <code>bisect.insort</code></li>
<li><strong>Use when:</strong> you need fast lookups by a known key</li>
</ul>
<h3 id="hashed-table">HASHED TABLE</h3>
<pre class="shiki shiki-themes github-light one-dark-pro" style="--shiki-light:#24292e;--shiki-dark:#abb2bf;--shiki-light-bg:#fff;--shiki-dark-bg:#282c34" tabindex="0"><code><span class="line"><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD">DATA</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">: lt_hashed</span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD"> TYPE HASHED TABLE OF</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> ty_employee</span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD"> WITH UNIQUE KEY</span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD"> name</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">.</span></span></code></pre>
<ul>
<li>Rows stored in a hash map by key</li>
<li>Access by key: fastest (O(1) — constant time)</li>
<li>No index access — can't use <code>sy-tabix</code></li>
<li><strong>Think of it as:</strong> Python's <code>dict</code> or Java's <code>HashMap</code></li>
<li><strong>Use when:</strong> you need very fast lookups by key on large datasets</li>
</ul>
<h3 id="performance-comparison">Performance Comparison</h3>
<pre><code>Operation              STANDARD    SORTED     HASHED
──────────────────     ─────────   ─────────  ─────────
APPEND/INSERT          O(1)        O(log n)   O(1)
READ by key            O(n)        O(log n)   O(1)
READ by index          O(1)        O(1)       N/A
LOOP (full scan)       O(n)        O(n)       O(n)
DELETE by key          O(n)        O(log n)   O(1)
</code></pre>
<p><strong>For most programs, STANDARD TABLE is fine.</strong> Only switch to SORTED or HASHED when you have large tables (10,000+ rows) and do frequent key lookups.</p>

<span class="line"><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD">TRY</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">.</span></span>
<span class="line"><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD">    DATA</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">(</span><span style="--shiki-light:#24292E;--shiki-dark:#E06C75">ls_found</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">) </span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD">=</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> lt_employees[ </span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD">name</span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD"> =</span><span style="--shiki-light:#032F62;--shiki-dark:#98C379"> 'Charlie'</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> ].</span></span>

<h2 id="the-work-area-pattern">The Work Area Pattern</h2>
<p>The traditional ABAP pattern uses a work area as a buffer between the program and the table:</p>
<pre class="shiki shiki-themes github-light one-dark-pro" style="--shiki-light:#24292e;--shiki-dark:#abb2bf;--shiki-light-bg:#fff;--shiki-dark-bg:#282c34" tabindex="0"><code><span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic">* Fill via work area</span></span>

<p><code>CLEAR</code> resets all fields to their initial values — essential before reusing a work area. Without it, fields from the previous row leak into the next one.</p>
<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Forgetting CLEAR before reusing a work area.</strong> If you APPEND a row, then change only the name field and APPEND again, the department and salary from the first row carry over. Always CLEAR the work area before building a new row.</li>
<li><strong>Using READ TABLE without checking sy-subrc.</strong> If the row isn't found, the work area retains its previous values — you'll process stale data without realizing it. Always check <code>sy-subrc = 0</code>.</li>
<li><strong>Using STANDARD TABLE for frequent key lookups on large data.</strong> READ TABLE on a STANDARD TABLE scans linearly — fine for 100 rows, terrible for 100,000. Use SORTED or HASHED for large lookup tables.</li>
<li><strong>Confusing table types after the fact.</strong> You choose the table type at declaration. You can't change a STANDARD TABLE to a HASHED TABLE later. Choose based on your access pattern.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>Internal tables are ABAP's core data structure — like Python lists but with structured rows and typed keys.</li>
<li>Three types: STANDARD (general purpose), SORTED (fast binary search), HASHED (fastest key lookup).</li>
<li>Fill with APPEND or VALUE constructor. Read with READ TABLE, table expressions, or LOOP AT.</li>
<li>Always check <code>sy-subrc</code> after READ TABLE — 0 = found, 4 = not found.</li>
<li>Always CLEAR the work area before building a new row.</li>
<li>Use <code>lines()</code> for count, <code>line_exists()</code> for existence checks.</li>
</ul>
