3:T2d69,<h1 id="sap-system-landscape--dev-quality-and-production">SAP System Landscape — Dev, Quality, and Production</h1>
<div data-cw-section="learn-box"><h2 id="what-youll-learn">What You'll Learn</h2>
<ul>
<li>Why SAP uses a three-system landscape (dev → QA → prod)</li>
<li>What the transport system is and how code moves between systems</li>
<li>What clients are and how they isolate data</li>
<li>How this compares to Git-based deployment workflows you already know</li>
</ul>
</div><h2 id="the-three-system-landscape">The Three-System Landscape</h2>
<p>In web development, you might deploy code like this:</p>
<pre><code>laptop → git push → GitHub → CI/CD → staging → production
</code></pre>
<p>SAP does something similar, but with its own terminology and a much more rigid process:</p>
<pre><code>DEV (Development)  →  QAS (Quality Assurance)  →  PRD (Production)
     Write code          Test it                    Users use it
</code></pre>
<p>Each of these is a separate SAP system — its own server, its own database, its own copy of SAP. They're connected by the <strong>transport system</strong>, which is SAP's version of a deployment pipeline.</p>
<h3 id="why-three-systems">Why Three Systems?</h3>
<p>The same reason you don't test in production. SAP runs mission-critical business processes — payroll, financial reporting, supply chain. A bug in production can mean employees don't get paid or financial statements are wrong. The three-system landscape ensures:</p>
<ul>
<li><strong>DEV</strong> — developers write and test code freely. Breaking things here is expected.</li>
<li><strong>QAS</strong> — business users test the changes with real-like data. Bugs caught here don't affect real operations.</li>
<li><strong>PRD</strong> — the live system. Only tested, approved code reaches here.</li>
</ul>
<p><strong>You NEVER write code directly in production.</strong> In SAP, this isn't just a best practice — the system physically prevents it. Production systems are locked for development.</p>
<h2 id="the-transport-system">The Transport System</h2>
<p>When you finish writing code in DEV, you don't copy files. You create a <strong>transport request</strong> — a container that holds your changes. Think of it like a commit + pull request + deployment package, all in one.</p>
<pre><code>Developer writes code in DEV
    ↓
Creates a transport request (like a commit)
    ↓
Releases the transport (like pushing to a branch)
    ↓
Transport is imported to QAS (like deploying to staging)
    ↓
Business users test in QAS
    ↓
Transport is imported to PRD (like deploying to production)
</code></pre>
<h3 id="transport-request-anatomy">Transport Request Anatomy</h3>
<p>A transport request has:</p>
<ul>
<li>A unique ID (e.g., <code>DEVK900123</code>)</li>
<li>An owner (the developer)</li>
<li>A description ("Add custom pricing validation for US orders")</li>
<li>One or more tasks (sub-items, one per developer if it's a team effort)</li>
<li>Objects (the actual code, tables, configurations being transported)</li>
</ul>
<pre class="shiki shiki-themes github-light one-dark-pro" style="--shiki-light:#24292e;--shiki-dark:#abb2bf;--shiki-light-bg:#fff;--shiki-dark-bg:#282c34" tabindex="0"><code><span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic">* You'll see transport requests when you create or modify objects</span></span>
<span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic">* SAP asks: "Assign to which transport request?"</span></span>
<span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic">* You either create a new one or add to an existing one</span></span></code></pre>
<h3 id="key-rule-transports-only-move-forward">Key Rule: Transports Only Move Forward</h3>
<pre><code>DEV → QAS → PRD     ✓  Forward — this is how it works
PRD → DEV            ✗  Never — you don't import production into development
QAS → DEV            ✗  Never — changes don't flow backward
</code></pre>
<p>If you need to fix a bug found in QAS, you fix it in DEV, create a new transport, and move it forward again.</p>
<h2 id="clients--data-isolation-within-a-system">Clients — Data Isolation Within a System</h2>
<p>Each SAP system has multiple <strong>clients</strong> — think of them as isolated tenants sharing the same system. Each client has its own data but shares the same code.</p>
<pre><code>DEV System
├── Client 100 — Development (your main workspace)
├── Client 200 — Unit testing
└── Client 300 — Sandbox (experimental)

QAS System
├── Client 100 — Integration testing
└── Client 200 — User acceptance testing

PRD System
└── Client 100 — Production (live business data)
</code></pre>
<p>When you log in to SAP, you specify three things:</p>
<ol>
<li><strong>System</strong> — which SAP system (DEV, QAS, PRD)</li>
<li><strong>Client</strong> — which client within that system (100, 200, etc.)</li>
<li><strong>User</strong> — your username and password</li>
</ol>
<h3 id="client-dependent-vs-client-independent">Client-Dependent vs Client-Independent</h3>
<ul>
<li><strong>Client-dependent data</strong> — business data (customers, orders, invoices). Different in every client.</li>
<li><strong>Client-independent data</strong> — programs (ABAP code), data dictionary objects. Same across all clients in a system.</li>
</ul>
<p>This means when you write ABAP code in Client 100 of DEV, it's automatically visible in Client 200 and 300 of DEV too — because code is client-independent. But the business data you test with is separate in each client.</p>
<h2 id="comparing-to-what-you-know">Comparing to What You Know</h2>
<pre><code>SAP Concept          Git/DevOps Equivalent
──────────────────   ──────────────────────────
DEV system           Local development environment
QAS system           Staging / pre-production
PRD system           Production
Transport request    Git commit + pull request + deploy
Client               Database schema or tenant
T-code SE09          Git log / PR dashboard
Transport release    Merge + deploy trigger
Basis administrator  DevOps / platform engineer
</code></pre>
<p>The biggest difference: in Git-based workflows, deployments are automated and fast (seconds to minutes). In SAP, transports can take 10-30 minutes to import and require a <strong>Basis administrator</strong> (SAP's version of a DevOps engineer) to schedule and execute them.</p>
<h2 id="the-basis-team">The Basis Team</h2>
<p>You'll hear "Basis" a lot. The Basis team manages the SAP infrastructure:</p>
<ul>
<li>Installing and patching SAP systems</li>
<li>Managing transports between systems</li>
<li>Monitoring system performance</li>
<li>Managing user accounts and authorizations</li>
<li>Database administration</li>
</ul>
<p>As an ABAP developer, you don't manage infrastructure. You write code in DEV, create transports, and the Basis team imports them to QAS and PRD. This separation exists because SAP systems are complex — a wrong transport to production can bring down an entire company's operations.</p>
<h2 id="your-first-transport--what-to-expect">Your First Transport — What to Expect</h2>
<p>When you create your first ABAP program (next lesson), SAP will immediately ask you for a transport request. Here's the flow:</p>
<ol>
<li>Open SE38 (ABAP Editor) in the DEV system</li>
<li>Create a new program <code>Z_MY_FIRST_PROGRAM</code></li>
<li>SAP prompts: "Assign to transport request?"</li>
<li>You either create a new request or use an existing one</li>
<li>Write your code, activate it (compile)</li>
<li>Test it in DEV</li>
<li>When ready, release the transport via SE09 (Transport Organizer)</li>
</ol>
<p>Don't worry about transports too much right now — we'll handle them naturally as we write programs. Just understand that every change you make is tracked and packaged for deployment.</p>
<h2 id="the-z-and-y-naming-convention">The "Z" and "Y" Naming Convention</h2>
<p>SAP reserves certain naming prefixes:</p>
<ul>
<li><strong>No prefix</strong> — SAP standard objects (you can't modify these)</li>
<li><strong>Z</strong> or <strong>Y</strong> prefix — custom objects (your code goes here)</li>
</ul>
<p>When you create a program, table, function module, or class, the name must start with Z or Y. This ensures your custom code never conflicts with SAP's standard code, even after upgrades.</p>
<pre class="shiki shiki-themes github-light one-dark-pro" style="--shiki-light:#24292e;--shiki-dark:#abb2bf;--shiki-light-bg:#fff;--shiki-dark-bg:#282c34" tabindex="0"><code><span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic">* SAP standard program — you can look but not touch</span></span>
<span class="line"><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD">REPORT</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> SAPMV45A.  </span><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic">" Standard sales order program</span></span>
<span class="line"></span>
<span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic">* Your custom program — you own this</span></span>
<span class="line"><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD">REPORT</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> Z_CUSTOM_SALES_REPORT.</span></span></code></pre>
<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Developing in the wrong client.</strong> If you accidentally log into Client 200 (testing) instead of Client 100 (development), your code changes are still visible (code is client-independent), but your test data configurations might be different. Always check which client you're in.</li>
<li><strong>Forgetting to release the transport.</strong> You can write code all day, but if you don't release the transport request, nothing moves to QAS. Unreleased transports are the SAP equivalent of uncommitted code.</li>
<li><strong>Creating too many transport requests.</strong> Each transport is a deployment unit. If you create 50 transports for one feature, the Basis team has to import 50 transports in the right order. Group related changes into one transport.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>SAP uses a three-system landscape: DEV → QAS → PRD. Code only moves forward.</li>
<li>The transport system packages your changes and moves them between systems — like a combined commit + deploy.</li>
<li>Clients isolate data within a system. Code is shared across clients; data is not.</li>
<li>All custom code starts with Z or Y to avoid conflicts with SAP standard.</li>
<li>The Basis team manages infrastructure and transports. You write code and create transport requests.</li>
</ul>
