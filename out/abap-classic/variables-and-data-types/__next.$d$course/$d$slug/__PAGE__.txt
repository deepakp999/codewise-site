<p><strong>Coming from Python:</strong> In Python you write <code>name = "Alice"</code> — no type declaration needed. ABAP requires explicit types: <code>DATA lv_name TYPE string.</code> then <code>lv_name = 'Alice'.</code> This is closer to Java's <code>String name = "Alice";</code> but even more verbose.</p>

<p><strong>When to use which:</strong></p>
<ul>
<li><code>i</code> — counters, loop indexes, quantities (whole numbers)</li>
<li><code>p</code> — money, financial calculations (exact decimals, no rounding errors)</li>
<li><code>f</code> — scientific calculations (rare in business applications)</li>
<li><code>int8</code> — very large whole numbers</li>
</ul>
<p><strong>Critical rule:</strong> Never use <code>f</code> (float) for financial data. Use <code>p</code> (packed decimal). <code>0.1 + 0.2</code> in floating point doesn't equal <code>0.3</code> — this matters when your report is for a CFO.</p>

<p><strong><code>c</code> vs <code>string</code>:</strong> Use <code>c</code> (fixed-length) when the data always has the same length — country codes (2 chars), material numbers (18 chars), plant codes (4 chars). Use <code>string</code> for free text — names, descriptions, addresses.</p>
<p><strong><code>n</code> (numeric character):</strong> Looks like a number but is stored as text. Leading zeros are preserved: <code>'0042'</code> stays <code>'0042'</code>, not <code>42</code>. SAP uses this for document numbers, org codes, and IDs.</p>

<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Using <code>f</code> (float) for currency amounts.</strong> Always use <code>p DECIMALS 2</code> for money. Floating-point arithmetic has rounding errors: <code>0.1 + 0.2 = 0.30000000000000004</code>. Packed decimal is exact.</li>
<li><strong>Forgetting that <code>c</code> type is space-padded.</strong> A <code>TYPE c LENGTH 10</code> variable containing <code>'Hello'</code> actually contains <code>'Hello     '</code> (5 chars + 5 spaces). Comparisons and concatenations can produce unexpected results if you don't trim.</li>
<li><strong>Not initializing variables.</strong> Unlike Python, ABAP initializes variables to type-specific defaults: <code>i</code> = 0, <code>string</code> = '' (empty), <code>d</code> = '00000000'. But relying on defaults makes code unclear — always set initial values explicitly when they matter.</li>
<li><strong>Confusing <code>n</code> and <code>i</code> types.</strong> <code>TYPE n LENGTH 4</code> is text that looks like a number — <code>'0042'</code> preserves the leading zero. <code>TYPE i</code> is an actual integer — <code>42</code>. Use <code>n</code> for document numbers and codes, <code>i</code> for calculations.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>Declare variables with <code>DATA</code>, constants with <code>CONSTANTS</code>. Use meaningful prefixes (<code>lv_</code>, <code>lc_</code>, <code>lt_</code>).</li>
<li>Use <code>p DECIMALS n</code> for financial calculations, <code>i</code> for whole numbers, <code>string</code> for free text.</li>
<li><code>TYPE d</code> stores dates as <code>YYYYMMDD</code>, <code>TYPE t</code> stores times as <code>HHMMSS</code>.</li>
<li><code>sy-subrc</code> is checked after every operation — 0 means success.</li>
<li>Inline declarations (<code>DATA(lv_x) = ...</code>) are modern ABAP — cleaner but not universal yet.</li>
<li>Reference SAP Data Dictionary types (<code>TYPE kunnr</code>, <code>TYPE matnr</code>) instead of raw types when working with SAP data.</li>
</ul>
