<h2 id="table-types">Table Types</h2>
<p>A table type explicitly defines the table's access type and key:</p>
<pre class="shiki shiki-themes github-light one-dark-pro" style="--shiki-light:#24292e;--shiki-dark:#abb2bf;--shiki-light-bg:#fff;--shiki-dark-bg:#282c34" tabindex="0"><code><span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic">* Standard table (most common)</span></span>
<span class="line"><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD">TYPES</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">: tt_orders</span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD"> TYPE STANDARD TABLE OF</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> ty_order</span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD"> WITH DEFAULT KEY</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">.</span></span>
<span class="line"></span>
<span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic">* Sorted table with explicit key</span></span>
<span class="line"><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD">TYPES</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">: tt_orders_sorted</span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD"> TYPE SORTED TABLE OF</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> ty_order</span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD"> WITH UNIQUE KEY</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> order_id.</span></span>
<span class="line"></span>
<span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic">* Hashed table</span></span>

<span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic">* Use in method signatures</span></span>

<h3 id="range-components">Range Components</h3>
<p>Each range row has four fields:</p>
<pre><code>SIGN    'I' = Include, 'E' = Exclude

LOW     Start value (or the single value for EQ)
HIGH    End value (only for BT = Between)
</code></pre>

<p>INCLUDE TYPE inlines all fields from another structure — like composition/inheritance for data types.</p>
<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Forgetting the SIGN field in ranges.</strong> Without <code>sign = 'I'</code>, the range condition doesn't include anything. Always set SIGN explicitly.</li>
<li><strong>Using an empty range in a SELECT WHERE ... IN.</strong> An empty range (<code>lr_kunnr IS INITIAL</code>) matches ALL rows — no filtering happens. Check before using: <code>IF lr_kunnr IS NOT INITIAL.</code></li>
<li><strong>Confusing TYPES and DATA.</strong> <code>TYPES</code> creates a blueprint (no memory allocated). <code>DATA</code> creates an actual variable (memory allocated). You can't WRITE to a TYPE or APPEND to a TYPE — only to DATA variables.</li>
<li><strong>Forgetting WITH DEFAULT KEY on table types.</strong> Without a key specification, some table type declarations cause syntax warnings or errors in strict mode.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li><code>TYPES</code> defines reusable blueprints for structures and table types.</li>
<li>Table types with explicit keys are required for method parameters.</li>
<li>Nested structures use chained dashes: <code>ls_record-address-city</code>.</li>
<li>RANGE tables store flexible selection criteria (SIGN, OPTION, LOW, HIGH).</li>
<li>Ranges integrate directly with SELECT ... WHERE ... IN — dynamically build your WHERE clauses.</li>
<li>Use INCLUDE TYPE to compose structures from reusable parts.</li>
<li>An empty range in WHERE ... IN matches everything — always check IS NOT INITIAL.</li>
</ul>
