</div><h2 id="the-data-migration-problem">The Data Migration Problem</h2>
<p>When a company goes live on SAP (or migrates to S/4HANA), they need to load existing data — customers, materials, open orders, GL balances. This data comes from legacy systems in formats like CSV, Excel, or flat files.</p>
<p>The challenge: SAP transactions have complex validation rules, authorization checks, and workflow triggers. You can't just INSERT into database tables — that bypasses all business logic and leaves the system in an inconsistent state.</p>
<p><strong>BDC solves this</strong> by simulating what a user would do: open a transaction, fill in fields, click buttons, and save. SAP processes each "session" as if a real user performed it, with all validations intact.</p>
<h2 id="bdc--batch-data-communication">BDC — Batch Data Communication</h2>
<h3 id="step-1-record-a-transaction-with-shdb">Step 1: Record a Transaction with SHDB</h3>
<p>Open transaction SHDB (Transaction Recorder) and create a new recording:</p>
<ol>
<li>Enter a recording name (e.g., <code>Z_CREATE_CUSTOMER</code>)</li>
<li>Enter the transaction to record (e.g., <code>XD01</code> — Create Customer)</li>
<li>Click "Start Recording"</li>
<li>SAP opens XD01. Fill in the fields as a normal user would.</li>
<li>Save the customer. The recording captures every screen, every field, every value.</li>
<li>Click "Back" to stop recording.</li>
</ol>
<p>The recording produces a BDC table — a sequence of screen numbers, field names, and values:</p>
<pre><code>Program          Screen    Field Name        Field Value

<h3 id="bdc-modes">BDC Modes</h3>
<pre><code>Mode    Behavior
─────   ─────────────────────────────────
'A'     Display All — shows every screen (for debugging)
'E'     Display on Error — shows screen only when an error occurs
'N'     No Display — runs in background (for production migration)
</code></pre>
<p>Always develop with mode 'A' (see every screen), test with 'E' (see errors), and run production migration with 'N' (fastest).</p>
<h2 id="lsmw--legacy-system-migration-workbench">LSMW — Legacy System Migration Workbench</h2>
<p>LSMW (transaction LSMW) is a wizard-based tool for data migration — no ABAP coding required. It provides:</p>
<ol>
<li><strong>Source structure</strong> — define the format of your legacy file (CSV, Excel)</li>
<li><strong>Target structure</strong> — map to SAP fields</li>
<li><strong>Field mapping</strong> — connect source fields to target fields with optional transformation rules</li>
<li><strong>Recording</strong> — SHDB recording of the target transaction</li>
<li><strong>Execution</strong> — read file, convert data, run BDC sessions in batch</li>
</ol>
<p>LSMW is preferred by functional consultants who don't write ABAP. It's slower than custom BDC programs but requires no coding.</p>
<h2 id="when-to-use-which-technique">When to Use Which Technique</h2>
<pre><code>Technique    Best For                        Speed     Coding Required
──────────   ─────────────────────────────   ─────     ───────────────
BAPI         Creating business objects       Fast      Yes (ABAP)
BDC          Screen-based transactions       Medium    Yes (ABAP)
LSMW         Configuration-based migration   Medium    No
IDoc         System-to-system migration      Medium    Minimal
Direct Input SAP-provided programs           Fastest   No
</code></pre>
<p><strong>BAPI is preferred</strong> when one exists for your scenario — it's faster and more reliable than BDC. <strong>BDC is necessary</strong> when there's no BAPI (many older transactions lack BAPIs). <strong>LSMW</strong> is for functional consultants doing one-time loads.</p>
<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Not using mode 'A' during development.</strong> Developing BDC blind (mode 'N') means you can't see which screen or field is causing the error. Always develop with mode 'A'.</li>
<li><strong>Hardcoding field values from the recording.</strong> A recording captures your specific test data. Replace hardcoded values with variables from your input file or selection screen.</li>
<li><strong>Not handling mandatory fields that appear conditionally.</strong> Some SAP screens show different fields based on previous inputs. Your BDC recording may not capture all possible screen variations.</li>
<li><strong>Using BDC when a BAPI exists.</strong> BDC is slower, more fragile (breaks if SAP changes screen layouts in upgrades), and harder to error-handle. Always check for a BAPI first.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>BDC simulates user transactions — it fills screens and clicks buttons programmatically.</li>
<li>Record transactions with SHDB to capture screen sequences and field names.</li>
<li>Use CALL TRANSACTION for real-time processing, BDC sessions (SM35) for batch processing.</li>
<li>LSMW is the no-code alternative for data migration — wizard-based, popular with functional consultants.</li>
<li>Always prefer BAPIs over BDC when available — BAPIs are faster, more stable, and better for error handling.</li>
<li>Develop in mode 'A', test in mode 'E', run production in mode 'N'.</li>
</ul>
