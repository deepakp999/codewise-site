<p>When you run this program (F8), it stops at <code>BREAK-POINT</code> and opens the debugger.</p>
<h3 id="method-2-set-a-breakpoint-in-the-editor">Method 2: Set a breakpoint in the editor</h3>
<p>In SE38 or Eclipse ADT, click in the margin next to a line number to set a breakpoint (or press the breakpoint button). These are <strong>session breakpoints</strong> — they only apply to your session and disappear when you log off.</p>
<h3 id="method-3-use-h-in-the-command-field">Method 3: Use /h in the command field</h3>
<p>Type <code>/h</code> in the SAP GUI command field and press Enter. The next action you take (clicking a button, pressing F8) will trigger the debugger. This is invaluable for debugging transactions — type <code>/h</code>, then execute the transaction, and you're in the debugger.</p>
<h2 id="the-debugger-interface">The Debugger Interface</h2>
<p>The ABAP Debugger (new debugger, available since NW 7.0) has four main areas:</p>
<pre><code>┌──────────────────────────────────────────────────────┐
│ Source Code                                           │ ← Current line highlighted
│   lv_total = lv_total + sy-index.                    │
├──────────────────────────────────────────────────────┤
│ Variables          │ Call Stack                        │
│ lv_total = 6       │ Z_DEBUG_DEMO (line 7)            │
│ sy-index = 3       │                                   │
│ sy-subrc = 0       │                                   │
├──────────────────────────────────────────────────────┤
│ Breakpoints / Watchpoints / Objects                   │
└──────────────────────────────────────────────────────┘
</code></pre>
<h2 id="stepping-through-code">Stepping Through Code</h2>
<pre><code>F5    Single Step     — execute one line, step INTO subroutines/methods
F6    Execute         — execute one line, step OVER subroutines/methods
F7    Return          — execute until current subroutine/method returns
F8    Continue        — run until next breakpoint (or program ends)
</code></pre>
<p><strong>F5 vs F6:</strong> If the current line calls a method, F5 jumps into the method's code. F6 executes the entire method and stops at the next line. Use F5 to debug inside a method, F6 to skip over it.</p>
<h2 id="inspecting-variables">Inspecting Variables</h2>
<p>In the debugger's variable display area, you can:</p>
<ul>
<li><strong>Double-click</strong> a variable name in the source code to add it to the watch list</li>
<li><strong>Type</strong> a variable name in the variable input field and press Enter</li>
<li><strong>View internal tables</strong> by double-clicking the table variable — shows all rows</li>
</ul>
<h3 id="viewing-internal-tables">Viewing Internal Tables</h3>
<pre><code>Double-click lt_employees in the code
→ Opens table viewer showing all rows and columns
→ You can scroll, filter, and search within the table
</code></pre>
<h3 id="modifying-variables-at-runtime">Modifying Variables at Runtime</h3>
<p>You can change variable values while debugging — useful for testing different scenarios:</p>
<ol>
<li>Double-click the variable to show its value</li>
<li>Change the value in the input field</li>
<li>Press Enter or click the pencil icon</li>
</ol>
<pre><code>lv_total = 6  → change to 100 → press Enter
Now lv_total = 100 and the program continues with this value
</code></pre>
<p><strong>Warning:</strong> Only do this for debugging. Don't "fix" production issues by modifying variables in the debugger — fix the code instead.</p>
<h2 id="watchpoints--break-when-a-value-changes">Watchpoints — Break When a Value Changes</h2>
<p>Watchpoints stop execution when a specific variable changes value:</p>
<ol>
<li>In the debugger, go to the Watchpoints tab</li>
<li>Enter the variable name (e.g., <code>lv_total</code>)</li>
<li>Optionally set a condition (e.g., <code>lv_total > 10</code>)</li>
<li>Press F8 (Continue) — execution stops when the condition is met</li>
</ol>
<p>This is invaluable for finding where a value gets corrupted: "When does <code>lv_status</code> change from 'A' to 'X'?" Set a watchpoint and run — the debugger stops at the exact line where the change happens.</p>
<h2 id="debugging-common-scenarios">Debugging Common Scenarios</h2>
<h3 id="short-dump-runtime-error">Short Dump (Runtime Error)</h3>
<p>When a program crashes, SAP creates a short dump viewable in ST22:</p>
<ol>
<li>Open ST22</li>
<li>Find your dump (sorted by date/time)</li>
<li>Read the error type (e.g., <code>COMPUTE_INT_ZERODIV</code> = division by zero)</li>
<li>Note the program name and line number</li>
<li>Open the program, set a breakpoint before that line</li>
<li>Run and debug to find the root cause</li>
</ol>
<h3 id="wrong-output">Wrong Output</h3>
<p>The report runs but shows wrong numbers:</p>
<ol>
<li>Set a breakpoint before the output section</li>
<li>Inspect the internal table that feeds the output</li>
<li>Step backward through the logic to find where the data goes wrong</li>
<li>Check: wrong SELECT? Missing WHERE condition? Wrong calculation?</li>
</ol>
<h3 id="infinite-loop">Infinite Loop</h3>
<p>The program hangs and doesn't complete:</p>
<ol>
<li>In SAP GUI, go to System → Cancel (or press the red X button)</li>
<li>SAP may offer to debug — accept</li>
<li>Check <code>sy-index</code> or the loop counter to see how many iterations happened</li>
<li>Inspect the loop condition — why isn't it terminating?</li>
</ol>
<h2 id="performance-debugging--se30--sat">Performance Debugging — SE30 / SAT</h2>
<p>Transaction SE30 (or SAT in newer systems) provides runtime analysis:</p>
<pre><code>1. Enter your program name in SE30
2. Click Execute
3. After the program runs, view the analysis:
   - Which statements took the most time?
   - How many database calls were made?
   - Which function modules were called and how often?
</code></pre>
<p>The analysis shows you exactly where time is spent. If 90% of time is in a SELECT inside a LOOP, you know to use FOR ALL ENTRIES instead.</p>
<h2 id="debugging-tips-from-senior-developers">Debugging Tips from Senior Developers</h2>
<ol>
<li>
<p><strong>Start from the output and work backward.</strong> If the report shows wrong data, start at the WRITE/ALV call and trace the data source backward through the code.</p>
</li>
<li>
<p><strong>Use the call stack.</strong> The call stack shows you which method called which. If you're lost in nested calls, the call stack is your map.</p>
</li>
<li>
<p><strong>Keep a notepad open.</strong> Write down variable values at key points. Patterns emerge that you can't see in the debugger alone.</p>
</li>
<li>
<p><strong>Learn the keyboard shortcuts.</strong> F5/F6/F7/F8 become muscle memory after a week. Clicking buttons is slow.</p>
</li>
<li>
<p><strong>Debug the standard code too.</strong> When a BAPI returns an error, F5 into the BAPI to see exactly which validation failed. SAP standard code is readable — you're allowed to look at it.</p>
</li>
</ol>
<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Using BREAK-POINT in production code.</strong> <code>BREAK-POINT</code> stops execution for every user. Use <code>BREAK username.</code> to stop only for your user, or use session breakpoints instead of hard-coded ones.</li>
<li><strong>Modifying variables in the debugger and thinking the bug is fixed.</strong> Changing a variable at runtime is a diagnostic tool, not a fix. Fix the source code.</li>
<li><strong>Ignoring the call stack.</strong> When you hit a breakpoint in a subroutine and don't know how you got there, check the call stack — it shows the full chain of callers.</li>
<li><strong>Not using SE30/SAT for performance issues.</strong> If a program is "slow," don't guess — profile it with SE30. The bottleneck is almost always a database call in a loop.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>F5 (step into), F6 (step over), F7 (return), F8 (continue) are your core debugger controls.</li>
<li><code>/h</code> in the command field activates debugging for the next action — works on any transaction.</li>
<li>Watchpoints stop execution when a variable changes — essential for tracking data corruption.</li>
<li>ST22 shows short dumps (runtime errors) with the exact program, line, and error type.</li>
<li>SE30/SAT profiles performance — use it before guessing at optimizations.</li>
<li>Use <code>BREAK username.</code> instead of <code>BREAK-POINT</code> to avoid stopping other users.</li>
</ul>
