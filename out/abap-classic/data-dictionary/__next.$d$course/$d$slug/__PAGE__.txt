<ul>
<li>What the Data Dictionary is and why it's central to SAP</li>
<li>The hierarchy: domains → data elements → table fields</li>

</ul>
</div><h2 id="what-is-the-data-dictionary">What Is the Data Dictionary?</h2>
<p>The Data Dictionary (transaction SE11) is SAP's metadata layer. It defines every database table, every data type, and every structure in the entire SAP system. If internal tables are ABAP's most important data structure, the Data Dictionary is its most important tool.</p>
<p>Think of it as a schema registry — like a database's <code>information_schema</code>, but richer. It defines not just column names and types, but also labels, documentation, validation rules, and relationships.</p>
<h2 id="the-building-blocks">The Building Blocks</h2>
<h3 id="domain--data-element--table-field">Domain → Data Element → Table Field</h3>
<p>SAP uses a three-layer type system:</p>
<pre><code>Domain          → defines the TECHNICAL properties (type, length, value range)
  └── Data Element → adds SEMANTIC meaning (labels, documentation)
       └── Table Field → uses the data element in a specific table
</code></pre>
<p><strong>Example:</strong></p>
<pre><code>Domain: CHAR10           → Type C, Length 10
  └── Data Element: KUNNR  → Label "Customer Number", help text, search help
       └── Table KNA1, field KUNNR  → The customer number column in the customer master
       └── Table VBAK, field KUNNR  → The customer number column in sales order header
</code></pre>
<p>The beauty: both KNA1 and VBAK reference the same data element KUNNR. If SAP changes the customer number format, both tables adapt automatically. And any program using <code>TYPE kunnr</code> gets the change for free.</p>
<h2 id="exploring-the-data-dictionary-in-se11">Exploring the Data Dictionary in SE11</h2>
<p>Type <code>/nSE11</code> and enter a table name:</p>
<h3 id="viewing-a-standard-table">Viewing a Standard Table</h3>
<pre><code>Table: KNA1 (Customer Master — General Data)

Key fields:
  MANDT    (Client)           TYPE MANDT
  KUNNR    (Customer Number)  TYPE KUNNR

Other fields:
  NAME1    (Name 1)           TYPE NAME1_GP
  LAND1    (Country)          TYPE LAND1_GP
  ORT01    (City)             TYPE ORT01
  PSTLZ    (Postal Code)     TYPE PSTLZ
  STRAS    (Street)           TYPE STRAS_GP
  ...
</code></pre>
<p>Click on any field to see its data element. Click on the data element to see its domain. This chain — table → data element → domain — is how you trace any field's definition in SAP.</p>
<h3 id="common-sap-tables-youll-work-with">Common SAP Tables You'll Work With</h3>
<pre><code>Table     Module    Description

KNA1      SD/FI     Customer master (general)

</code></pre>
<h2 id="creating-a-custom-table">Creating a Custom Table</h2>
<p>In SE11, enter a table name starting with Z (e.g., <code>ZEMPLOYEES</code>) and click "Create."</p>
<h3 id="step-1-delivery-and-maintenance">Step 1: Delivery and Maintenance</h3>
<ul>
<li><strong>Delivery Class:</strong> A (Application table — contains your business data)</li>
<li><strong>Data Browser/Table View Maintenance:</strong> choose "Display/Maintenance Allowed"</li>
</ul>
<h3 id="step-2-define-fields">Step 2: Define Fields</h3>
<pre><code>Field Name    Key?   Data Element     Type      Length    Description
───────────   ─────  ──────────────   ────────  ──────   ──────────────
MANDT         ✓      MANDT            CLNT      3        Client
EMPLOYEE_ID   ✓      ZEMPLOYEE_ID     NUMC      10       Employee ID
NAME          -      ZENAME           CHAR      50       Employee Name
DEPARTMENT    -      ZDEPARTMENT      CHAR      30       Department
SALARY        -      ZSALARY          CURR      13,2     Salary
HIRE_DATE     -      ZHIRE_DATE       DATS      8        Hire Date
</code></pre>
<h3 id="step-3-technical-settings">Step 3: Technical Settings</h3>
<p>Every table needs technical settings:</p>
<ul>
<li><strong>Data Class:</strong> APPL0 (master data), APPL1 (transaction data), or APPL2 (configuration)</li>
<li><strong>Size Category:</strong> 0-4 (expected number of records)</li>
<li><strong>Buffering:</strong> Not buffered (default for transaction data)</li>
</ul>
<h3 id="step-4-activate">Step 4: Activate</h3>
<p>Save and activate (Ctrl+F3). The table is now created in the database — you can write ABAP programs that read and write to it.</p>
<h2 id="structures">Structures</h2>
<p>A structure is a data type without a database table — it defines a row shape but doesn't store data:</p>
<pre class="shiki shiki-themes github-light one-dark-pro" style="--shiki-light:#24292e;--shiki-dark:#abb2bf;--shiki-light-bg:#fff;--shiki-dark-bg:#282c34" tabindex="0"><code><span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic">* Using a structure from the dictionary</span></span>
<span class="line"><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD">DATA</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">: ls_customer</span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD"> TYPE</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> kna1.   </span><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic">" Has all fields of table KNA1</span></span>
<span class="line"></span>
<span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic">* Or define your own in code</span></span>
<span class="line"><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD">TYPES</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">: </span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD">BEGIN OF</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> ty_order_summary,</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">         order_id   </span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD"> TYPE</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> vbeln,</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">         customer   </span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD"> TYPE</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> kunnr,</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">         total      </span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD"> TYPE</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> netwr_ap,</span></span>
<span class="line"><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD">       END OF</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> ty_order_summary.</span></span></code></pre>
<p>Structures defined in SE11 are reusable across all programs. Structures defined with <code>TYPES</code> in code are local to that program.</p>
<h2 id="table-types">Table Types</h2>
<p>A table type defines the type of an internal table — useful for method parameters:</p>
<pre class="shiki shiki-themes github-light one-dark-pro" style="--shiki-light:#24292e;--shiki-dark:#abb2bf;--shiki-light-bg:#fff;--shiki-dark-bg:#282c34" tabindex="0"><code><span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic">* In SE11, you'd create a table type ZEMPLOYEE_TAB as:</span></span>
<span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic">*   Line Type: ZEMPLOYEES (your table structure)</span></span>
<span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic">*   Access: Standard Table</span></span>
<span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic">*   Key: EMPLOYEE_ID</span></span>
<span class="line"></span>
<span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic">* In code, equivalent to:</span></span>
<span class="line"><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD">TYPES</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">: tt_employees</span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD"> TYPE STANDARD TABLE OF</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> zemployees</span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD"> WITH KEY</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> employee_id.</span></span></code></pre>
<h2 id="search-helps">Search Helps</h2>
<p>Search helps (F4 help) define the dropdown values when a user presses F4 on an input field. They're defined in SE11 and attached to data elements.</p>
<p>When you press F4 on a customer number field, the search help queries KNA1, shows a list of customers with their names and cities, and lets the user pick one. This is configured in the Data Dictionary, not in program code.</p>

<span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic">* Reference a specific field's type</span></span>

<span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic">* Reference a data element directly</span></span>

<p>This is the preferred way to declare variables in production code — reference the dictionary type, not raw types. If SAP changes the field length, your variable adapts automatically.</p>
<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Creating tables without MANDT (client field).</strong> Almost every SAP table has MANDT as the first key field for client isolation. Without it, your data isn't client-dependent, which causes issues in multi-client systems.</li>
<li><strong>Using raw types instead of data elements.</strong> <code>DATA: lv_id TYPE c LENGTH 10.</code> works, but <code>DATA: lv_id TYPE kunnr.</code> is better — it inherits labels, documentation, and search helps from the data element.</li>
<li><strong>Forgetting to activate technical settings.</strong> A table without technical settings can't be activated. You must specify data class and size category.</li>
<li><strong>Not checking existing SAP tables first.</strong> Before creating a custom table, check if SAP already has one that fits. SAP has thousands of standard tables — duplicating them creates maintenance headaches during upgrades.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>The Data Dictionary (SE11) is SAP's metadata layer — it defines every table, type, and structure.</li>
<li>The hierarchy is: Domain (technical) → Data Element (semantic) → Table Field (usage).</li>
<li>Always reference dictionary types in your programs (<code>TYPE kunnr</code>) instead of raw types (<code>TYPE c LENGTH 10</code>).</li>
<li>Custom tables start with Z or Y, must have MANDT as first key field, and need technical settings.</li>
<li>Structures define row shapes without database storage. Table types define internal table types for reuse.</li>
<li>Explore existing SAP tables before creating custom ones.</li>
</ul>
