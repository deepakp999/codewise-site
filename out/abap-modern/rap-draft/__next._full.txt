1b:T21aa,<h1 id="draft-handling--save-incomplete-work">Draft Handling — Save Incomplete Work</h1>
<div data-cw-section="learn-box"><h2 id="what-youll-learn">What You'll Learn</h2>
<ul>
<li>What draft handling is and why it matters</li>
<li>How draft works technically (draft tables, draft actions)</li>
<li>The draft lifecycle: new → edit → activate/discard</li>
<li>Side effects — refresh fields after changes</li>
<li>Draft-specific behavior features</li>
</ul>
</div><h2 id="why-draft">Why Draft?</h2>
<p>Without draft, users must complete and save in a single session. Close the browser? Data gone. Network hiccup? Data gone. Need approval from a colleague before saving? You can't.</p>
<p>Draft handling stores incomplete data in a separate draft table. Users can:</p>
<ul>
<li>Start editing and come back hours later</li>
<li>Switch devices mid-edit</li>
<li>Get interrupted without losing work</li>
<li>Share draft for review before finalizing</li>
</ul>
<p>Every production Fiori app uses draft. It's not optional — it's expected.</p>
<h2 id="how-we-already-enabled-draft">How We Already Enabled Draft</h2>
<p>In Lesson 14, we added <code>with draft</code> and <code>draft table</code> to the behavior definition:</p>
<pre><code>managed implementation in class zbp_i_tm_salesorder unique;
with draft;

define behavior for ZI_TM_SalesOrder alias SalesOrder
persistent table ztm_salesorder
draft table ztm_so_d          -- Draft data goes here
lock master total etag LastChangedAt
{
  ...
}
</code></pre>
<p>The <code>draft table</code> is a copy of the persistent table with additional draft metadata columns. ADT generates it for you — use the quick fix (Ctrl+1) on the behavior definition.</p>
<h2 id="the-draft-lifecycle">The Draft Lifecycle</h2>
<pre><code>1. User clicks CREATE or EDIT
   → Framework creates a draft record in ztm_so_d
   → Persistent table is unchanged

2. User edits fields, adds line items
   → Changes saved to draft table automatically
   → Determinations with "on modify" fire
   → No changes to persistent table yet

3. User clicks SAVE (Activate)
   → Validations run ("on save")
   → If valid: draft → persistent table, draft deleted
   → If invalid: errors shown, draft preserved

4. User clicks DISCARD (Cancel)
   → Draft deleted, no changes to persistent table
</code></pre>
<h2 id="draft-actions-in-the-behavior-definition">Draft Actions in the Behavior Definition</h2>
<p>Draft adds these automatic actions:</p>
<pre><code>define behavior for ZI_TM_SalesOrder alias SalesOrder
{
  ...
  draft action Edit;               -- Enter edit mode (create draft from active)
  draft action Activate;            -- Save (move draft to active)
  draft action Discard;             -- Cancel (delete draft)
  draft action Resume;              -- Continue editing a saved draft
  draft determine action Prepare;   -- Validate before activating
}
</code></pre>
<p>These are generated automatically when you declare <code>with draft</code>. You don't implement them — the framework handles them.</p>
<h2 id="the-prepare-action">The <code>Prepare</code> Action</h2>
<p><code>draft determine action Prepare</code> runs all <code>on save</code> validations when the user clicks Save, BEFORE actually activating the draft. If validations fail, the draft stays, and the user sees error messages.</p>
<p>This is how RAP separates "save draft" (automatic, no validation) from "activate" (validation required).</p>
<h2 id="side-effects--real-time-ui-updates">Side Effects — Real-Time UI Updates</h2>
<p>When a user changes a field, you often want other fields to update immediately. For example: changing an item's quantity should recalculate the order total.</p>
<p>Declare side effects in the behavior definition:</p>
<pre><code>define behavior for ZI_TM_SalesOrderItem alias SalesOrderItem
{
  ...
  side effects {
    field Quantity affects field _SalesOrder.TotalAmount;
    field Price affects field _SalesOrder.TotalAmount;
  }
}
</code></pre>
<p>When <code>Quantity</code> changes, the framework:</p>
<ol>
<li>Runs the <code>determineTotal</code> determination (on modify)</li>
<li>Refreshes the <code>TotalAmount</code> field in the Fiori UI</li>
</ol>
<p>No manual UI refresh needed.</p>

<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Strict validation in draft mode</strong> — Users expect to save partial work. Don't reject drafts for empty required fields. Validate strictly only in <code>on save</code> / Prepare.</li>
<li><strong>Forgetting draft tables for children</strong> — Every entity in the BO hierarchy needs its own draft table. Parent AND child.</li>
<li><strong>Not declaring <code>with draft</code> on associations</strong> — The behavior definition must say <code>association _Items { create; with draft; }</code> — the <code>with draft</code> is required.</li>
<li><strong>Heavy on modify determinations</strong> — In draft mode, <code>on modify</code> fires on every field change. Keep these lightweight.</li>
<li><strong>Not testing draft → activate flow</strong> — The Fiori preview's Save button activates the draft. Test the full cycle: create → edit → save → verify active data.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>Draft stores incomplete data in a separate table — users can save, leave, and resume.</li>
<li>Draft is enabled with <code>with draft</code> + <code>draft table</code> in the behavior definition.</li>
<li>The lifecycle: Edit → draft saved automatically → Activate (validates + persists) or Discard.</li>
<li>Side effects refresh related fields in real-time when data changes during editing.</li>
<li>Validate leniently in draft mode, strictly on activation (Prepare action).</li>
</ul>
