<div data-cw-section="learn-box"><h2 id="what-youll-learn">What You'll Learn</h2>
<ul>
<li>The extensibility model in ABAP Cloud</li>
<li>Developer extensibility: on-stack with released BADIs</li>
<li>Side-by-side extensibility: separate apps on BTP</li>
<li>Key-user extensibility: no-code extensions</li>
<li>Choosing the right extensibility approach</li>
</ul>
</div><h2 id="techmarts-extensibility-challenge">TechMart's Extensibility Challenge</h2>
<p>TechMart acquires "GadgetWorld." GadgetWorld needs additional fields on the Sales Order — a warranty flag and a returns policy reference. TechMart's Sales Order BO was built clean. How do you add these fields without modifying the original code?</p>
<h2 id="three-extensibility-approaches">Three Extensibility Approaches</h2>
<h3 id="1-developer-extensibility-on-stack">1. Developer Extensibility (On-Stack)</h3>
<p>Add custom logic using released extension points — BADIs, extend behavior definitions, additional CDS fields.</p>

<p>You can add new validations, determinations, and actions to an existing BO without modifying the original:</p>

  validation validateWarranty on save { field WarrantyFlag; }
  determination determineReturnsPolicy on modify { field ReturnsPolicy; }

</code></pre>

<h3 id="2-side-by-side-extensibility-btp">2. Side-by-Side Extensibility (BTP)</h3>
<p>Build a separate application on SAP BTP that communicates with the core S/4HANA system via released APIs:</p>
<pre><code>S/4HANA Core System          SAP BTP
┌────────────────────┐       ┌──────────────────────┐
│ Sales Order BO     │ ←API→ │ Warranty Management  │
│ (unchanged)        │       │ App (custom)          │
│                    │       │                       │
│ Released OData API │───────│ Reads orders via API  │
│                    │       │ Stores warranty data  │
│                    │       │ in BTP database       │
└────────────────────┘       └──────────────────────┘
</code></pre>
<p>Use side-by-side when:</p>
<ul>
<li>The extension is complex (its own data model, workflow, UI)</li>
<li>The core system shouldn't carry the custom logic load</li>
<li>You need technologies not available in ABAP (ML models, external APIs)</li>
<li>The extension has its own lifecycle (different team, different release cycle)</li>
</ul>
<h3 id="3-key-user-extensibility-no-code">3. Key-User Extensibility (No-Code)</h3>
<p>For business users who need simple extensions:</p>
<ul>
<li>Add custom fields via the Fiori "Custom Fields" app</li>
<li>Create custom logic with BTP Workflow</li>
<li>Add custom tiles and pages</li>
</ul>
<p>No developer involvement needed. Limited but powerful for simple cases.</p>
<h2 id="choosing-the-right-approach">Choosing the Right Approach</h2>
<table>
<thead>
<tr>
<th>Scenario</th>
<th>Approach</th>
<th>Why</th>
</tr>
</thead>
<tbody>
<tr>
<td>Add a field + simple validation</td>
<td>Developer (on-stack)</td>
<td>Minimal effort, stays in ABAP</td>
</tr>
<tr>
<td>Build a warranty management app</td>
<td>Side-by-side (BTP)</td>
<td>Separate concerns, own data model</td>
</tr>
<tr>
<td>Add a field for reporting only</td>
<td>Key-user</td>
<td>No developer needed</td>
</tr>
<tr>
<td>Integrate with external warranty API</td>
<td>Side-by-side (BTP)</td>
<td>External communication, async</td>
</tr>
<tr>
<td>Add complex business rules to existing BO</td>
<td>Developer (on-stack)</td>
<td>Deep integration with BO lifecycle</td>
</tr>
<tr>
<td>Build an ML model for demand forecasting</td>
<td>Side-by-side (BTP)</td>
<td>Different technology stack</td>
</tr>
</tbody>
</table>
<p><strong>Rule of thumb:</strong> Start with the simplest approach. Key-user if possible, developer on-stack if business logic is needed, side-by-side only for complex standalone functionality.</p>
<h2 id="clean-core-and-extensibility-levels">Clean Core and Extensibility Levels</h2>
<p>Remember the levels from Lesson 2:</p>
<ul>
<li><strong>Level A</strong> — All extensions use released APIs and extension points. Fully upgrade-safe.</li>
<li><strong>Level B</strong> — Uses stable but unreleased APIs. Acceptable with governance.</li>
<li><strong>Level C/D</strong> — Uses internal APIs or modifications. Not upgrade-safe.</li>
</ul>
<p>GadgetWorld's extension should be Level A:</p>
<ul>
<li>CDS view extensions (released feature)</li>
<li>Behavior extensions (released feature)</li>
<li>Released BADIs (guaranteed stable)</li>
<li>BTP communication via released OData APIs</li>
</ul>
<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Modifying the original BO</strong> — The whole point of extensibility is NOT touching the original. If you change <code>ZI_TM_SalesOrder</code> directly, you're creating Level C/D technical debt.</li>
<li><strong>Using unreleased BADIs</strong> — Not all BADIs are released for cloud. Check the API state in ADT before implementing.</li>
<li><strong>Side-by-side for simple fields</strong> — Don't build a BTP app just to add one field. Use on-stack developer extensibility.</li>
<li><strong>Ignoring key-user extensibility</strong> — If a business user just needs one extra field for reporting, they can add it themselves. No developer ticket needed.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>ABAP Cloud offers three extensibility approaches: developer (on-stack), side-by-side (BTP), and key-user (no-code).</li>
<li>CDS views and behavior definitions can be extended without modification using <code>EXTEND VIEW ENTITY</code> and <code>extend behavior</code>.</li>
<li>Side-by-side extensions on BTP communicate via released APIs — separate concerns, separate lifecycle.</li>
<li>Always aim for Level A extensibility — use only released extension points.</li>
<li>Start simple (key-user), escalate to developer, then side-by-side only when needed.</li>
</ul>
