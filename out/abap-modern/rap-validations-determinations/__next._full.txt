<div data-cw-section="learn-box"><h2 id="what-youll-learn">What You'll Learn</h2>
<ul>
<li>Validations: reject invalid data before save</li>

</ul>
</div><h2 id="validations--reject-bad-data">Validations — Reject Bad Data</h2>
<p>A validation checks data and rejects the save if something is wrong. It doesn't change data — it only accepts or rejects.</p>
<p><strong>Step 1: Declare in behavior definition</strong></p>
<pre><code>define behavior for ZI_TM_SalesOrder alias SalesOrder
{
  ...
  validation validateCustomer on save { create; update;
    field CustomerId; }
  validation validateStatus on save { create; update;
    field Status; }
}
</code></pre>
<p><code>on save</code> means the validation runs when the user clicks Save. <code>field CustomerId</code> means it triggers when that field changes.</p>

<h2 id="determinations--auto-calculate-values">Determinations — Auto-Calculate Values</h2>
<p>A determination automatically sets field values when data changes. It modifies data — the opposite of a validation.</p>
<p><strong>Step 1: Declare in behavior definition</strong></p>
<pre><code>define behavior for ZI_TM_SalesOrder alias SalesOrder
{
  ...
  determination determineOrderId on save { create; }
  determination determineTotal on modify { field Currency;
    create; }
}
</code></pre>
<p><code>on save</code> runs once when saving. <code>on modify</code> runs immediately when a field changes (useful for real-time calculations in draft mode).</p>

<h2 id="on-save-vs-on-modify">On Save vs On Modify</h2>
<table>
<thead>
<tr>
<th>Timing</th>
<th>When It Runs</th>
<th>Best For</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>on save</code></td>
<td>User clicks Save</td>
<td>Final checks, number generation, validation</td>
</tr>
<tr>
<td><code>on modify</code></td>
<td>Immediately on field change</td>
<td>Real-time calculations, auto-fill, UI responsiveness</td>
</tr>
</tbody>
</table>
<p><code>on modify</code> is more responsive but runs more often. Keep the logic lightweight.</p>
<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Validations that modify data</strong> — Validations should only check and report. Use determinations to change data.</li>
<li><strong>Determinations that reject</strong> — Determinations should only set values. Use validations to reject.</li>
<li><strong>Not using IN LOCAL MODE</strong> — Inside handlers, always read/modify with <code>IN LOCAL MODE</code> to avoid authorization loops.</li>
<li><strong>Heavy logic in on modify</strong> — <code>on modify</code> runs on every field change. If your determination does a complex aggregation, it'll fire constantly during editing. Use <code>on save</code> for expensive operations.</li>
<li><strong>Missing %tky</strong> — Always use <code>%tky</code> (transactional key) from the <code>keys</code> parameter. Using <code>%key</code> can fail in draft scenarios.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>Validations reject bad data (check + report errors). Determinations auto-fill data (read + modify).</li>
<li><code>on save</code> runs at save time. <code>on modify</code> runs immediately on field change.</li>
<li>Always append to <code>failed</code> and <code>reported</code> in validations. Use <code>%element</code> to highlight specific fields.</li>
<li>Determinations use <code>MODIFY ENTITIES IN LOCAL MODE</code> to update the current BO data.</li>
<li>Keep <code>on modify</code> determinations lightweight; use <code>on save</code> for expensive operations.</li>
</ul>
