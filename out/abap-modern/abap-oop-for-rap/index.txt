1b:T7e44,<h1 id="oop-refresher--interfaces-abstract-classes-and-the-rap-connection">OOP Refresher — Interfaces, Abstract Classes, and the RAP Connection</h1>
<div data-cw-section="learn-box"><h2 id="what-youll-learn">What You'll Learn</h2>
<ul>
<li>Why OOP is the foundation of RAP (not optional — mandatory)</li>
<li>Interfaces in ABAP Cloud — the contract pattern</li>
<li>Abstract classes and method templates</li>
<li>How RAP behavior implementations use these OOP patterns</li>
<li>A preview of what RAP handler classes look like</li>
</ul>
</div><h2 id="why-this-lesson-exists">Why This Lesson Exists</h2>
<p>In the Classic course, you learned OOP as one of many approaches. You could write a report without classes. You could use function modules instead of methods. OOP was a best practice, not a requirement.</p>
<p>In ABAP Cloud, <strong>OOP is the only way to write executable code.</strong> There are no reports (SE38), no function modules (SE37), no subroutines (FORM/ENDFORM). Everything is a class.</p>
<p>RAP takes this further. When you define a business object's behavior (validations, actions, determinations), the framework generates a class skeleton. You fill in the methods. The pattern is always the same: interface → class → method implementation.</p>

<p>See the pattern?</p>
<ol>
<li>The class <strong>inherits</strong> from <code>cl_abap_behavior_handler</code> (an abstract class from the framework)</li>
<li>The methods are <strong>defined by the framework</strong> (you don't choose the signatures)</li>
<li>You <strong>implement the body</strong> — that's your business logic</li>
<li>The framework <strong>calls your methods</strong> at the right time (on save, on modify, on action)</li>
</ol>
<p>This is the interface/abstract-class/template-method pattern from OOP textbooks, applied at industrial scale.</p>

<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>"I'll skip OOP and learn RAP directly"</strong> — RAP IS OOP. Every behavior implementation is a class. Every validation is a method. If interfaces and inheritance confuse you, go back to the Classic OOP lessons before continuing.</li>
<li><strong>Trying to use procedural code in behavior implementations</strong> — You can't write <code>PERFORM</code> or <code>CALL FUNCTION</code> inside RAP handler methods. Everything is a method call on a class.</li>
<li><strong>Overcomplicating class hierarchies</strong> — RAP keeps it simple: one handler class per entity, methods per behavior feature. Don't create deep inheritance trees. RAP doesn't need them.</li>
<li><strong>Ignoring the <code>LOCAL MODE</code> keyword</strong> — When reading data inside a handler, you use <code>IN LOCAL MODE</code> to bypass authorization (you're already inside the BO). Forgetting this causes authorization failures.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>In ABAP Cloud, OOP is mandatory — there's no procedural alternative.</li>
<li>Interfaces define contracts (what methods must exist). RAP uses this pattern for behavior implementations.</li>
<li>Abstract classes provide templates. RAP handler classes inherit from <code>cl_abap_behavior_handler</code> and implement framework-defined methods.</li>
<li>RAP behavior implementation = OOP template method pattern. The framework calls your methods; you provide the business logic.</li>
<li>You don't need advanced OOP (multiple inheritance, design patterns beyond the basics). RAP keeps the class structure simple and predictable.</li>
</ul>
