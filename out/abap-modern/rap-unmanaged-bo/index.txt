1b:T4b89,<h1 id="unmanaged-rap--when-you-need-full-control">Unmanaged RAP — When You Need Full Control</h1>
<div data-cw-section="learn-box"><h2 id="what-youll-learn">What You'll Learn</h2>
<ul>
<li>When to choose unmanaged over managed RAP</li>
<li>The unmanaged save sequence</li>
<li>Wrapping existing BAPI logic in a RAP service</li>
<li>The interaction phase vs save phase</li>
<li>Migration path from unmanaged to managed</li>
</ul>
</div><h2 id="when-to-use-unmanaged">When to Use Unmanaged</h2>
<p>Managed RAP handles persistence automatically — the framework generates INSERT/UPDATE/DELETE. But what if:</p>
<ul>
<li>You have existing BAPI logic for order processing that's been tested for years?</li>
<li>Your data is stored across multiple tables with complex relationships?</li>
<li>You need custom locking beyond what managed provides?</li>
<li>You're integrating with non-ABAP systems?</li>
</ul>
<p>Unmanaged RAP gives you the RAP service layer (OData, Fiori, EML) while you keep full control of persistence.</p>
<h2 id="the-behavior-definition">The Behavior Definition</h2>
<pre><code>unmanaged implementation in class zbp_i_tm_legacy_order unique;
strict ( 2 );

define behavior for ZI_TM_LegacyOrder alias LegacyOrder
lock master
authorization master ( global )
etag master LastChangedAt
{
  create;
  update;
  delete;

  mapping for ztm_legacy_order corresponding { ... }
}
</code></pre>
<p>The only difference from managed: <code>unmanaged</code> instead of <code>managed</code> on the first line.</p>
<h2 id="the-save-sequence">The Save Sequence</h2>
<p>In unmanaged RAP, you implement the save yourself. The framework splits the transaction into two phases:</p>
<p><strong>Interaction Phase</strong> — User is editing. Data is in a transactional buffer (memory). No database writes yet.</p>
<p><strong>Save Phase</strong> — User clicks Save. The framework calls your save methods to persist the buffer to the database.</p>

<h2 id="migration-path">Migration Path</h2>
<p>Many teams start unmanaged (to wrap legacy code) and migrate to managed over time:</p>
<ol>
<li><strong>Phase 1:</strong> Unmanaged RAP wrapping existing BAPIs → immediate Fiori/OData benefit</li>
<li><strong>Phase 2:</strong> Gradually move persistence logic from BAPIs to managed RAP</li>
<li><strong>Phase 3:</strong> Full managed RAP with validations, actions, draft</li>
</ol>
<p>This is TechMart's approach for the legacy order system.</p>
<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Starting with unmanaged for new apps</strong> — If there's no legacy code to wrap, use managed. It's less code and more framework support.</li>
<li><strong>Forgetting the saver class</strong> — Unmanaged MUST have a saver class with <code>save_modified</code>. Without it, nothing persists.</li>
<li><strong>Calling COMMIT WORK in the saver</strong> — The framework handles COMMIT. Your saver does INSERT/UPDATE/DELETE only.</li>
<li><strong>Not handling all three operations</strong> — Check <code>create</code>, <code>update</code>, AND <code>delete</code> in <code>save_modified</code>. Missing one means that operation silently does nothing.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>Unmanaged RAP gives you the service layer (OData, Fiori, EML) while you control persistence.</li>
<li>You implement <code>save_modified</code> in a saver class — handling creates, updates, and deletes to the database.</li>
<li>Ideal for wrapping legacy BAPIs and complex persistence scenarios.</li>
<li>Start unmanaged for legacy integration, migrate to managed when ready.</li>
<li>For new applications with no legacy constraints, always use managed.</li>
</ul>
