</div><h2 id="what-are-annotations">What Are Annotations?</h2>
<p>Annotations are metadata that you attach to CDS views and fields. They don't change the data — they tell consumers (Fiori, OData, analytics) <strong>how</strong> to use the data.</p>
<p>Think of annotations like labels on a shipping box. The box content (data) doesn't change, but the labels tell the handler: "Fragile" (display as read-only), "This Side Up" (show in this position on the UI), "Express" (searchable, high priority).</p>
<p>In Classic ABAP, you'd control UI layout in dynpro screen painter or ALV field catalog. In modern ABAP, annotations do this declaratively — no code needed.</p>

<h2 id="metadata-extensions--keep-views-clean">Metadata Extensions — Keep Views Clean</h2>
<p>Putting dozens of UI annotations directly in a CDS view makes it hard to read. <strong>Metadata extensions</strong> separate UI concerns from data modeling:</p>
<pre class="shiki shiki-themes github-light one-dark-pro" style="--shiki-light:#24292e;--shiki-dark:#abb2bf;--shiki-light-bg:#fff;--shiki-dark-bg:#282c34" tabindex="0"><code><span class="line"><span style="--shiki-light:#032F62;--shiki-dark:#98C379">" Step 1: The CDS view stays clean — data only</span></span>
<span class="line"><span style="--shiki-light:#032F62;--shiki-dark:#98C379">@AccessControl.authorizationCheck: #NOT_REQUIRED</span></span>
<span class="line"><span style="--shiki-light:#032F62;--shiki-dark:#98C379">@EndUserText.label: 'TechMart Product'</span></span>
<span class="line"><span style="--shiki-light:#032F62;--shiki-dark:#98C379">@Metadata.allowExtensions: true   -- THIS enables metadata extensions</span></span>
<span class="line"></span>
<span class="line"><span style="--shiki-light:#032F62;--shiki-dark:#98C379">DEFINE VIEW ENTITY ZI_TM_Product</span></span>

<p><strong>Best practice:</strong> Always use metadata extensions for UI annotations. Keep the CDS view entity focused on data modeling. This separation is a Clean Core principle.</p>
<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Embedding UI annotations directly in interface views</strong> — Use metadata extensions instead. Interface views (<code>ZI_</code>) should be pure data models.</li>
<li><strong>Forgetting <code>@Metadata.allowExtensions: true</code></strong> — Without this, you can't create metadata extensions for the view.</li>
<li><strong>Wrong position numbering</strong> — Use increments of 10 (10, 20, 30) so you can insert fields later without renumbering.</li>
<li><strong>Overannotating</strong> — Not every field needs to be on every UI facet. Show only what users need.</li>
<li><strong>Ignoring <code>importance</code></strong> — On mobile devices, only <code>#HIGH</code> importance fields show. If your key fields are <code>#LOW</code>, mobile users see an empty list.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>Annotations are metadata that control how CDS data is consumed — by Fiori, OData, analytics, and search.</li>
<li>@UI annotations generate complete Fiori Elements UIs without frontend code. <code>lineItem</code> = list columns, <code>identification</code> = detail page, <code>selectionField</code> = search filters.</li>
<li>@Search annotations enable fuzzy full-text search in Fiori apps.</li>
<li>Metadata extensions separate UI concerns from data models — always use them for UI annotations.</li>
<li>Annotations are declarative — you describe WHAT you want, not HOW to build it.</li>
</ul>
