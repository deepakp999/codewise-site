</div><h2 id="the-problem-rap-solves">The Problem RAP Solves</h2>
<p>You've built CDS views that model TechMart's data beautifully. But CDS views are read-only. Users can't create a new sales order, update a status, or delete a cancelled order through a CDS view alone.</p>
<p>In Classic ABAP, you'd solve this with BAPIs, function modules, and dynpro transactions — writing hundreds of lines of boilerplate for CRUD operations, locking, authorization, validation, and error handling.</p>
<p>RAP eliminates that boilerplate. You define WHAT your business object does (create, update, delete, validate, execute actions), and the framework handles HOW — the OData service generation, the locking mechanism, the draft handling, the transaction management.</p>
<h2 id="the-three-layer-architecture">The Three-Layer Architecture</h2>
<p>Every RAP application has three layers:</p>
<pre><code>┌──────────────────────────────────────────┐
│  Layer 3: SERVICE                        │
│  Service Definition + Service Binding    │
│  → Exposes the BO as OData V2/V4        │
│  → Consumed by Fiori, external systems   │
├──────────────────────────────────────────┤
│  Layer 2: BEHAVIOR                       │
│  Behavior Definition + Implementation    │
│  → Defines CRUD, validations, actions    │
│  → Business logic lives here             │
├──────────────────────────────────────────┤
│  Layer 1: DATA MODEL                     │
│  CDS View Entities (Interface + Project) │
│  → The foundation you built in Module 2  │
│  → Compositions define the BO structure  │
└──────────────────────────────────────────┘
</code></pre>
<p>You've already built Layer 1. Modules 3 and 4 build Layers 2 and 3.</p>
<h2 id="the-three-implementation-types">The Three Implementation Types</h2>
<p>RAP offers three patterns for different scenarios:</p>
<p><strong>Managed (this course's focus):</strong>
The framework handles everything — database operations, locking, numbering, draft. You write only business logic (validations, actions, determinations). Best for new applications.</p>
<pre><code>You define:  "Sales Order has CRUD, validate customer, action approve"
RAP does:    INSERT/UPDATE/DELETE to database, lock handling, OData plumbing
</code></pre>
<p><strong>Unmanaged:</strong>
You handle database operations yourself. The framework provides the OData service and transaction framework, but you write the save logic. Best for wrapping existing code (BAPIs, legacy persistence).</p>
<pre><code>You define:  "Sales Order has CRUD" + you implement the SAVE method
RAP does:    OData plumbing, transaction coordination
You do:      INSERT/UPDATE/DELETE to database in your save method
</code></pre>
<p><strong>Query:</strong>
Read-only. No CRUD, no behavior. Used for analytical queries, search results, or data that comes from non-ABAP sources. Best for reporting views.</p>
<pre><code>You define:  "Product Report has read access"
RAP does:    OData query service
No create, update, or delete
</code></pre>
<p>For TechMart's Sales Order app, we'll use <strong>managed</strong> — it's the most productive and the recommended approach for new development.</p>
<h2 id="the-artifact-map">The Artifact Map</h2>
<p>Here's every artifact in a complete RAP application. Don't memorize this — we'll build each one step by step:</p>
<pre><code>ZI_TM_SalesOrder (Interface CDS View Entity)
    ↓ defines data model + compositions
ZI_TM_SalesOrderItem (Interface CDS View Entity - child)
    ↓
ZC_TM_SalesOrder (Projection CDS View Entity)
    ↓ selects fields for this specific app
ZC_TM_SalesOrderItem (Projection CDS View Entity - child)
    ↓
Behavior Definition: ZI_TM_SalesOrder
    ↓ defines CRUD, validations, actions
Behavior Projection: ZC_TM_SalesOrder
    ↓ exposes which behaviors this app uses
Behavior Implementation: zbp_i_tm_salesorder
    ↓ ABAP class with business logic
Service Definition: ZSD_TM_SALESORDER
    ↓ lists which entities to expose
Service Binding: ZSB_TM_SALESORDER_V4
    ↓ binds to OData V4 protocol
    ↓
Fiori Elements App (auto-generated from annotations)
</code></pre>
<p>That's 10+ artifacts, but each one is small and focused. The framework generates skeletons for most of them.</p>

<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Trying to build RAP without understanding CDS</strong> — RAP is built ON CDS. If compositions, associations, and annotations are unclear, go back to Module 2.</li>
<li><strong>Starting with unmanaged</strong> — Unmanaged is for legacy integration. Start with managed. It's simpler and teaches the patterns better.</li>
<li><strong>Thinking RAP replaces ABAP</strong> — RAP is a framework written in ABAP. Your business logic is still ABAP code in classes. RAP just provides the structure.</li>
<li><strong>Skipping the projection layer</strong> — You could expose interface views directly, but projections give you flexibility: one interface view, multiple projections for different apps.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>RAP is SAP's strategic framework for building transactional business applications in ABAP Cloud.</li>
<li>Three layers: data model (CDS), behavior (validations/actions), service (OData exposure).</li>
<li>Three types: managed (framework does persistence), unmanaged (you do persistence), query (read-only).</li>
<li>RAP integrates everything from Module 2 — CDS views, compositions, annotations, access control — into interactive applications.</li>
<li>Start with managed. It handles 90% of new application scenarios.</li>
</ul>
