<div data-cw-section="learn-box"><h2 id="what-youll-learn">What You'll Learn</h2>

</div><h2 id="associations-vs-compositions">Associations vs Compositions</h2>
<p>In Lesson 7, you learned associations — loose relationships between independent entities. A product exists independently of any order.</p>
<p>Compositions are different. They define <strong>ownership</strong>. A line item cannot exist without its sales order. Delete the order, and the items must go too. This is the parent-child pattern.</p>
<pre><code>Association: Order ←→ Customer     (independent entities, linked by reference)
Composition: Order ──► Line Items  (parent owns children, lifecycle bound)
</code></pre>
<p>In database terms: associations link entities with foreign keys. Compositions link entities with existence dependency.</p>

<p>The critical keywords:</p>
<ul>
<li><strong><code>COMPOSITION [0..*] OF</code></strong> — in the parent: "I own these children"</li>
<li><strong><code>ASSOCIATION TO PARENT</code></strong> — in the child: "I belong to this parent"</li>
</ul>
<h2 id="why-this-matters-for-rap">Why This Matters for RAP</h2>
<p>When we build the RAP business object in Module 3, this composition defines the BO structure:</p>
<pre><code>RAP Business Object: ZI_TM_SalesOrder
├── Root Entity: Sales Order (CRUD on orders)
└── Child Entity: Sales Order Item (CRUD on items, cascading delete)
</code></pre>
<p>RAP reads the composition and automatically:</p>
<ul>
<li>Creates items when creating an order</li>
<li>Deletes items when deleting an order</li>
<li>Locks the entire tree when editing</li>
<li>Validates parent and children together on save</li>
</ul>
<p>Without compositions, you'd code all of this manually. With compositions, it's declarative.</p>

<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Mixing up COMPOSITION and ASSOCIATION</strong> — If the child entity can't exist without the parent, it's a composition. If both entities are independent, it's an association.</li>
<li><strong>Forgetting TO PARENT in the child</strong> — The parent has <code>COMPOSITION OF child</code>. The child MUST have <code>ASSOCIATION TO PARENT parent</code>. Both sides are required.</li>
<li><strong>Wrong key structure</strong> — The child's key must include the parent's key. Sales Order Item has <code>key OrderId, key ItemId</code> — not just <code>key ItemId</code>.</li>
<li><strong>Projecting without REDIRECTED TO</strong> — When creating projection views with compositions, you must redirect the composition to the projected child using <code>REDIRECTED TO COMPOSITION CHILD</code>.</li>
<li><strong>Deep hierarchies</strong> — RAP supports grandchildren (Order → Item → Schedule Line), but keep hierarchies shallow. Two levels (parent + child) covers most business cases.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>Compositions define ownership hierarchies — the child's lifecycle depends on the parent.</li>
<li><code>COMPOSITION [0..*] OF</code> in the parent, <code>ASSOCIATION TO PARENT</code> in the child.</li>
<li>Compositions become the structure of RAP business objects — RAP auto-handles cascading create/delete/lock.</li>
<li>Projection views (<code>ZC_</code>) tailor interface views (<code>ZI_</code>) for specific consumers.</li>
<li>The pattern: Interface view → Projection view → Service → Fiori app.</li>
</ul>
