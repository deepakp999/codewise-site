1b:T6430,<h1 id="feature-control-and-authorization">Feature Control and Authorization</h1>
<div data-cw-section="learn-box"><h2 id="what-youll-learn">What You'll Learn</h2>
<ul>
<li>What feature control is and why it matters</li>
<li>Instance feature control: per-record dynamic behavior</li>
<li>Static feature control: global operation control</li>
<li>Field-level control: read-only fields based on status</li>
<li>RAP authorization checks</li>
</ul>
</div><h2 id="why-feature-control">Why Feature Control?</h2>
<p>Without feature control, every button and field is always available. Users can try to delete approved orders, edit completed orders, or approve already-approved orders. The validation would reject the action, but the user sees an error instead of not seeing the button at all.</p>
<p>Feature control prevents the action from being offered. No button = no confusion.</p>
<h2 id="instance-feature-control">Instance Feature Control</h2>
<p>Controls operations per record — "this specific order can/can't be edited."</p>
<p><strong>Step 1: Declare in behavior definition</strong></p>
<pre><code>define behavior for ZI_TM_SalesOrder alias SalesOrder
{
  ...
  action approve result [1] $self;
  
  instance features;  -- Enable instance feature control
}
</code></pre>

<h2 id="feature-control-vs-authorization-vs-validation">Feature Control vs Authorization vs Validation</h2>
<table>
<thead>
<tr>
<th>Mechanism</th>
<th>Purpose</th>
<th>When It Runs</th>
<th>Effect</th>
</tr>
</thead>
<tbody>
<tr>
<td>Feature Control</td>
<td>UI behavior — show/hide buttons</td>
<td>Before UI renders</td>
<td>Button hidden/disabled</td>
</tr>
<tr>
<td>Authorization</td>
<td>Access control — who can do what</td>
<td>On operation request</td>
<td>403 Unauthorized</td>
</tr>
<tr>
<td>Validation</td>
<td>Data quality — is the data valid</td>
<td>On save</td>
<td>Error message</td>
</tr>
</tbody>
</table>
<p>All three work together:</p>
<ol>
<li>Feature control hides the Approve button for non-New orders</li>
<li>Authorization checks if the user is allowed to approve</li>
<li>Validation confirms the data is valid for approval</li>
</ol>
<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Using validation instead of feature control</strong> — If an operation should never be available for a given status, use feature control to hide the button. Don't let users click it and then show an error.</li>
<li><strong>Forgetting to declare <code>instance features</code></strong> — Without this line in the behavior definition, <code>get_instance_features</code> is never called.</li>
<li><strong>Not returning results for all keys</strong> — The method receives a table of keys. Return feature control for EVERY key, not just the first one.</li>
<li><strong>Hardcoding authorization</strong> — Use SAP authorization objects, not hardcoded user checks.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>Feature control dynamically shows/hides operations and fields based on record state.</li>
<li>Instance feature control: per-record (approved orders can't be deleted). Static feature control: global (maintenance mode disables creation).</li>
<li>Field-level control: make fields read-only, mandatory, or unrestricted based on status.</li>
<li>Feature control, authorization, and validation are three complementary mechanisms — use all three.</li>
<li>Feature control improves UX by preventing impossible actions, not just rejecting them.</li>
</ul>
