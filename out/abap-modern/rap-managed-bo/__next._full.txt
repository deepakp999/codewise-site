<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Forgetting the mapping block</strong> — Without <code>mapping for ... corresponding</code>, the framework can't save CDS field values to table columns. Activation fails.</li>
<li><strong>Missing administrative fields</strong> — <code>@Semantics.user.createdBy</code>, <code>@Semantics.systemDateTime.createdAt</code>, etc. are required for managed BOs with draft. Skip them and draft breaks.</li>
<li><strong>Using sequential keys instead of UUIDs</strong> — Managed numbering works with UUIDs. If you want a human-readable order number, use a determination (Lesson 19) to generate it after creation.</li>
<li><strong>Forgetting <code>lock dependent by</code></strong> — Child entities must declare their lock dependency on the parent. Without it, concurrent editing can corrupt data.</li>
<li><strong>Not creating the draft tables</strong> — The <code>draft table</code> in the behavior definition must exist. ADT can generate them — use the quick fix.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>A managed RAP BO has: database tables, interface CDS views with compositions, behavior definition, behavior implementation class, projection views, and behavior projection.</li>
<li>The managed framework handles persistence (INSERT/UPDATE/DELETE), locking, draft, UUID numbering, and administrative fields automatically.</li>
<li><code>DEFINE ROOT VIEW ENTITY</code> marks the BO root. Children use <code>COMPOSITION</code>/<code>TO PARENT</code>.</li>
<li>The behavior definition is the central artifact — it declares CRUD, field properties, and maps CDS fields to table columns.</li>
<li>For a basic managed BO with no custom logic, the implementation class is nearly empty. The framework does the work.</li>
</ul>
