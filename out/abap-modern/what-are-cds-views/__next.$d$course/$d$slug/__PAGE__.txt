</div><h2 id="why-cds-views">Why CDS Views?</h2>
<p>In Classic ABAP, you modeled data in SE11 — tables, views, structures, data elements, domains. It worked, but it had limits. DDIC views couldn't have calculated fields. They couldn't define associations (only joins). They couldn't carry metadata about how the data should be displayed in a UI.</p>
<p>CDS views solve all of these problems. They are the <strong>single data modeling layer</strong> for modern SAP applications. Everything flows through CDS:</p>
<pre><code>Database Tables → CDS Views → RAP Business Objects → OData Services → Fiori Apps
</code></pre>
<p>Think of CDS views as intelligent windows into your data. A DDIC view was a static JOIN. A CDS view is a JOIN + calculated fields + annotations + associations + access control + parameter support — all defined in one place, executed on the database.</p>
<h2 id="define-view-vs-define-view-entity">DEFINE VIEW vs DEFINE VIEW ENTITY</h2>
<p>You'll see two syntaxes in the SAP ecosystem:</p>
<pre class="shiki shiki-themes github-light one-dark-pro" style="--shiki-light:#24292e;--shiki-dark:#abb2bf;--shiki-light-bg:#fff;--shiki-dark-bg:#282c34" tabindex="0"><code><span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic">-- OLD syntax (still works, but don't use for new development)</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#E06C75">@AbapCatalog</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">.sqlViewName: </span><span style="--shiki-light:#032F62;--shiki-dark:#98C379">'ZV_TM_PROD'</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">DEFINE VIEW ZI_TM_Product </span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD">AS</span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD"> SELECT</span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD"> FROM</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> ztm_product { ... }</span></span>
<span class="line"></span>
<span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic">-- NEW syntax (use this — it's the standard for ABAP Cloud)</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">DEFINE VIEW ENTITY ZI_TM_Product </span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD">AS</span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD"> SELECT</span><span style="--shiki-light:#D73A49;--shiki-dark:#C678DD"> FROM</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> ztm_product { ... }</span></span></code></pre>
<p><strong>Always use <code>DEFINE VIEW ENTITY</code></strong> for new development. The old <code>DEFINE VIEW</code> requires an SQL view name and has limitations. View entities are the standard for RAP and ABAP Cloud.</p>

<h2 id="code-pushdown--why-cds-is-fast">Code Pushdown — Why CDS Is Fast</h2>
<p>When you SELECT from a CDS view, the query executes on the database. The ABAP application server never sees the raw data — it gets the result set. This is called <strong>code pushdown</strong> — pushing computation to SAP HANA.</p>
<pre><code>Classic ABAP approach:
  Database → raw data → ABAP application server → process → result
  
CDS approach:
  Database → CDS view (joins, filters, calculations) → result → ABAP
</code></pre>
<p>For large datasets, this is dramatically faster. TechMart's sales analysis that took 30 seconds with Classic SELECT + LOOP + COLLECT now takes 2 seconds via a CDS view with aggregation.</p>
<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Forgetting <code>@AccessControl.authorizationCheck</code></strong> — Every CDS view needs this annotation. Use <code>#NOT_REQUIRED</code> during development, then add proper access control later (Lesson 12).</li>
<li><strong>Using <code>DEFINE VIEW</code> instead of <code>DEFINE VIEW ENTITY</code></strong> — The old syntax requires an SQL view name and has limitations. Always use <code>DEFINE VIEW ENTITY</code>.</li>
<li><strong>Not aliasing fields</strong> — Unaliased fields use database column names, which are often uppercase with underscores. CamelCase aliases are mandatory for Fiori and RAP compatibility.</li>
<li><strong>Forgetting to activate</strong> — CDS views must be activated (Ctrl+F3) before they appear in data preview or ABAP SQL.</li>
<li><strong>Trying to create CDS in SE11</strong> — CDS views can ONLY be created in ADT. They don't exist in the SE11 world.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>CDS views are the data modeling layer of modern ABAP. Everything — RAP, OData, Fiori — is built on CDS.</li>
<li>Use <code>DEFINE VIEW ENTITY</code> (not the old <code>DEFINE VIEW</code>) for all new development.</li>
<li>Alias fields to CamelCase with <code>AS</code>. Mark primary keys with <code>key</code>.</li>
<li>CDS views execute on the database (code pushdown), making them faster than Classic ABAP processing.</li>
<li>Naming convention: <code>ZI_</code> for interface views, <code>ZC_</code> for consumption views, <code>ZR_</code> for RAP root views.</li>
</ul>
