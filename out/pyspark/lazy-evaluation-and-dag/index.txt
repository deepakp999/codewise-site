<div data-cw-section="learn-box"><h2 id="what-youll-learn">What You'll Learn</h2>
<ul>
<li>Why Spark doesn't execute your code immediately</li>
<li>The difference between transformations and actions</li>
<li>What the DAG (Directed Acyclic Graph) is</li>

<li>How to use <code>explain()</code> to see Spark's execution plan</li>

</div><h2 id="the-mystery-from-lesson-2">The Mystery From Lesson 2</h2>
<p>Remember in Lesson 2, we noted that PySpark operations are lazy? You write <code>df.filter(...)</code>, and nothing happens until you call <code>.show()</code>. At the time, we said "Spark just remembers the instruction." Now let's understand why.</p>
<h2 id="transformations-vs-actions">Transformations vs Actions</h2>
<p>Every PySpark operation falls into one of two categories:</p>
<p><strong>Transformations</strong> — instructions that Spark records but doesn't execute:</p>
<ul>
<li><code>select()</code>, <code>filter()</code>, <code>where()</code>, <code>groupBy()</code>, <code>join()</code>, <code>withColumn()</code>, <code>orderBy()</code>, <code>distinct()</code>, <code>union()</code>, <code>repartition()</code></li>
</ul>
<p><strong>Actions</strong> — commands that trigger actual computation:</p>
<ul>
<li><code>show()</code>, <code>count()</code>, <code>collect()</code>, <code>first()</code>, <code>take()</code>, <code>write()</code>, <code>toPandas()</code></li>
</ul>

<h2 id="why-does-spark-wait">Why Does Spark Wait?</h2>
<p>Because waiting lets Spark optimize. Consider this example:</p>
<pre class="shiki shiki-themes github-light one-dark-pro" style="--shiki-light:#24292e;--shiki-dark:#abb2bf;--shiki-light-bg:#fff;--shiki-dark-bg:#282c34" tabindex="0"><code><span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic"># You write this:</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">result </span><span style="--shiki-light:#D73A49;--shiki-dark:#56B6C2">=</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> df.</span><span style="--shiki-light:#24292E;--shiki-dark:#61AFEF">select</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">(</span><span style="--shiki-light:#032F62;--shiki-dark:#98C379">"name"</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">, </span><span style="--shiki-light:#032F62;--shiki-dark:#98C379">"department"</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">, </span><span style="--shiki-light:#032F62;--shiki-dark:#98C379">"salary"</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">) \</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">    .</span><span style="--shiki-light:#24292E;--shiki-dark:#61AFEF">filter</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">(</span><span style="--shiki-light:#24292E;--shiki-dark:#61AFEF">col</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">(</span><span style="--shiki-light:#032F62;--shiki-dark:#98C379">"department"</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">) </span><span style="--shiki-light:#D73A49;--shiki-dark:#56B6C2">==</span><span style="--shiki-light:#032F62;--shiki-dark:#98C379"> "Engineering"</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">) \</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">    .</span><span style="--shiki-light:#24292E;--shiki-dark:#61AFEF">select</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">(</span><span style="--shiki-light:#032F62;--shiki-dark:#98C379">"name"</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">, </span><span style="--shiki-light:#032F62;--shiki-dark:#98C379">"salary"</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">)</span></span></code></pre>
<p>A naive engine would: (1) scan all columns, (2) filter rows, (3) drop the department column. Three passes over the data.</p>
<p>Spark's optimizer sees the full chain and realizes: "I only need <code>name</code> and <code>salary</code> for rows where <code>department == 'Engineering'</code>. I can do this in one pass — read only those three columns, filter immediately, and output two columns."</p>
<p>This optimization is only possible because Spark sees the entire chain before executing anything. If it executed each line immediately (like pandas does), it couldn't optimize across operations.</p>
<h2 id="the-dag">The DAG</h2>
<p>When you call an action like <code>.show()</code>, Spark builds a <strong>DAG</strong> — a Directed Acyclic Graph — of all the transformations needed to produce the result.</p>
<p>Think of it like a recipe: instead of executing each step as you write it, Spark collects all the steps, reorganizes them for efficiency, then executes the optimized version.</p>
<pre><code>Your code:
  df → filter(salary > 90000) → select(name, salary) → orderBy(salary) → show()

Spark's DAG:
  Stage 1: Scan data → filter → select (one pass, no shuffle)
  Stage 2: Sort by salary (requires shuffle)
  Action: show() displays the result
</code></pre>
<p>The DAG breaks your transformations into <strong>stages</strong>. A new stage starts whenever data needs to move between machines (a shuffle). Within a stage, everything runs in a single pass.</p>

<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Calling <code>.count()</code> to "check" your data between steps.</strong> Each <code>count()</code> triggers a full computation of everything above it. Use <code>.show(5)</code> or <code>.limit(5).show()</code> for quick peeks — they only compute enough data to show 5 rows, not the entire dataset.</li>
<li><strong>Thinking transformations are "free."</strong> Transformations don't execute immediately, but they do add steps to the DAG. Extremely long transformation chains can create complex plans that take longer to optimize. This is rarely a problem in practice, but it's worth knowing.</li>
<li><strong>Not using <code>explain()</code> on slow queries.</strong> If a query is slow, <code>explain()</code> is your first debugging tool. It shows you whether Spark is doing unnecessary shuffles, full table scans, or suboptimal join strategies.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>Transformations (filter, select, join, etc.) are recorded but not executed. Actions (show, count, write, etc.) trigger execution.</li>
<li>Spark builds a DAG of all transformations and optimizes the entire chain before running anything.</li>
<li>This lazy approach enables optimizations like column pruning, predicate pushdown, and join reordering.</li>
<li>Use <code>explain()</code> to see what Spark actually plans to do — read the physical plan from bottom to top.</li>
<li>Every action triggers a full recomputation. Use caching (Lesson 24) to avoid redundant work.</li>
</ul>
