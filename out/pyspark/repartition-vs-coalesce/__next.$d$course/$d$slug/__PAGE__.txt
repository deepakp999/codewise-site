3:T7fad,<h1 id="repartition-vs-coalesce--when-to-use-which">Repartition vs Coalesce — When to Use Which</h1>
<div data-cw-section="learn-box"><h2 id="what-youll-learn">What You'll Learn</h2>
<ul>
<li>The exact difference between <code>repartition</code> and <code>coalesce</code></li>
<li>When each one triggers (or avoids) a shuffle</li>
<li>Common patterns: writing fewer output files, pre-join partitioning, fixing skew</li>
<li>The cost-benefit trade-off for each approach</li>
</ul>
</div><h2 id="the-one-line-answer">The One-Line Answer</h2>
<ul>
<li><strong><code>repartition(n)</code></strong> — full shuffle, creates exactly n evenly distributed partitions. Can increase or decrease.</li>
<li><strong><code>coalesce(n)</code></strong> — no shuffle, combines adjacent partitions. Can only decrease. Partitions may be uneven.</li>
</ul>

<h2 id="the-decision-matrix">The Decision Matrix</h2>
<pre><code>Situation                              Use
────────────────────────────────────   ──────────────
Need FEWER partitions for output       coalesce(n)
Need MORE partitions for parallelism   repartition(n)
Need EVEN distribution                 repartition(n)
Pre-partitioning for a join            repartition(col)
Writing a single output file           coalesce(1)
After filter removed most data         coalesce(n)
Fixing data skew                       repartition(n)
</code></pre>

<p>Without the <code>repartition</code>, each output partition directory might contain files from many input partitions — creating many small files. With <code>repartition</code> by the same columns, each output directory gets one well-sized file.</p>
<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Using <code>coalesce(1)</code> on large datasets.</strong> This forces all data through a single partition — one core does all the work. Fine for 1000 rows, dangerous for 10 GB. If you need a single output file from a large dataset, consider: do you really need one file, or can downstream tools handle a directory of files?</li>
<li><strong>Using <code>repartition</code> when <code>coalesce</code> would work.</strong> If you're going from 200 partitions to 10, <code>coalesce(10)</code> avoids a shuffle. <code>repartition(10)</code> does the same thing but with an unnecessary shuffle. The only reason to prefer <code>repartition</code> when reducing is if you need perfectly even partition sizes.</li>
<li><strong>Forgetting that <code>coalesce</code> can create uneven partitions.</strong> If you have 8 partitions of sizes [100, 100, 100, 100, 100, 100, 100, 900] and coalesce to 4, you might get [200, 200, 200, 1000]. If this unevenness matters, use <code>repartition</code> instead.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li><code>coalesce(n)</code> — reduces partitions without a shuffle. Fast but may create uneven partitions.</li>
<li><code>repartition(n)</code> — full shuffle, creates exactly n even partitions. Can increase or decrease.</li>
<li><code>repartition(col)</code> — partitions by column value. Useful before joins and writes.</li>
<li>Use <code>coalesce</code> to reduce, <code>repartition</code> to increase or to get even distribution.</li>
<li>Always consider partition count when writing output — too many partitions = too many small files.</li>
<li>The shuffle cost of <code>repartition</code> is real — don't use it if <code>coalesce</code> achieves the same goal.</li>
</ul>
