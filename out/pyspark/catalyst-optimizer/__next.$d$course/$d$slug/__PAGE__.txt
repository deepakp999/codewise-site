<h2 id="key-optimizations">Key Optimizations</h2>
<h3 id="1-predicate-pushdown">1. Predicate Pushdown</h3>
<p>Catalyst pushes filters as close to the data source as possible:</p>
<pre class="shiki shiki-themes github-light one-dark-pro" style="--shiki-light:#24292e;--shiki-dark:#abb2bf;--shiki-light-bg:#fff;--shiki-dark-bg:#282c34" tabindex="0"><code><span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic"># You write this — filter AFTER select</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">result </span><span style="--shiki-light:#D73A49;--shiki-dark:#56B6C2">=</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> df.</span><span style="--shiki-light:#24292E;--shiki-dark:#61AFEF">select</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">(</span><span style="--shiki-light:#032F62;--shiki-dark:#98C379">"id"</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">, </span><span style="--shiki-light:#032F62;--shiki-dark:#98C379">"department"</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">, </span><span style="--shiki-light:#032F62;--shiki-dark:#98C379">"salary"</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">) \</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">    .</span><span style="--shiki-light:#24292E;--shiki-dark:#61AFEF">filter</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">(</span><span style="--shiki-light:#24292E;--shiki-dark:#61AFEF">col</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">(</span><span style="--shiki-light:#032F62;--shiki-dark:#98C379">"salary"</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">) </span><span style="--shiki-light:#D73A49;--shiki-dark:#56B6C2">></span><span style="--shiki-light:#005CC5;--shiki-dark:#D19A66"> 50000</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">)</span></span>
<span class="line"></span>
<span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic"># Catalyst rewrites it to — filter DURING scan</span></span>
<span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic"># Equivalent to: scan only rows where salary > 50000, then select columns</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">result.</span><span style="--shiki-light:#24292E;--shiki-dark:#61AFEF">explain</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">()</span></span></code></pre>
<p>With file formats like Parquet, predicate pushdown means Spark can skip entire file blocks that don't contain matching rows. If your Parquet is partitioned by <code>department</code> and you filter <code>WHERE department = 'Engineering'</code>, Spark only reads the Engineering directory. It doesn't even open the other files.</p>
<h3 id="2-column-pruning">2. Column Pruning</h3>
<p>Catalyst only reads the columns you actually use:</p>
<pre class="shiki shiki-themes github-light one-dark-pro" style="--shiki-light:#24292e;--shiki-dark:#abb2bf;--shiki-light-bg:#fff;--shiki-dark-bg:#282c34" tabindex="0"><code><span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic"># You select 3 out of 4 columns</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">result </span><span style="--shiki-light:#D73A49;--shiki-dark:#56B6C2">=</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> df.</span><span style="--shiki-light:#24292E;--shiki-dark:#61AFEF">select</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">(</span><span style="--shiki-light:#032F62;--shiki-dark:#98C379">"id"</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">, </span><span style="--shiki-light:#032F62;--shiki-dark:#98C379">"department"</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">, </span><span style="--shiki-light:#032F62;--shiki-dark:#98C379">"salary"</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">)</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">result.</span><span style="--shiki-light:#24292E;--shiki-dark:#61AFEF">explain</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">()</span></span></code></pre>
<p>In the physical plan, you'll see the scan only reads <code>id</code>, <code>department</code>, and <code>salary</code> — not <code>city</code>. With Parquet's columnar format, this means Spark physically skips the city column's data blocks. On a table with 50 columns where you only need 3, this is a 94% reduction in I/O.</p>
<p><strong>This is why explicit schemas matter</strong> (Lesson 7): when Spark knows the exact schema, it can prune columns at the storage level. With <code>inferSchema</code>, it may need to read more data to determine types.</p>

<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">df.</span><span style="--shiki-light:#24292E;--shiki-dark:#61AFEF">filter</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">(</span><span style="--shiki-light:#24292E;--shiki-dark:#61AFEF">col</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">(</span><span style="--shiki-light:#032F62;--shiki-dark:#98C379">"salary"</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">) </span><span style="--shiki-light:#D73A49;--shiki-dark:#56B6C2">></span><span style="--shiki-light:#005CC5;--shiki-dark:#D19A66"> 876000</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">)</span></span></code></pre>

<p>When you use a UDF in a filter, Catalyst can't push it down to the Parquet reader because it doesn't know what the UDF does. It has to read ALL the data, send it to Python, run the UDF, and then filter. Compare this to <code>col("salary") > 50000</code>, which Catalyst pushes all the way down to the file reader.</p>
<p><strong>This is the #1 reason UDFs are slow</strong> — not just the JVM-to-Python overhead, but the loss of all Catalyst optimizations.</p>
<h3 id="rdds">RDDs</h3>
<p>If you convert a DataFrame to an RDD (<code>.rdd</code>), Catalyst can no longer optimize it. DataFrames have schema information that Catalyst uses. RDDs don't.</p>

<span class="line"></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">result.</span><span style="--shiki-light:#24292E;--shiki-dark:#61AFEF">explain</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">()</span></span></code></pre>
<p>Read from bottom to top:</p>
<pre><code>== Physical Plan ==
*(2) HashAggregate(keys=[department], functions=[avg(salary)])
+- Exchange hashpartitioning(department, 200)     ← SHUFFLE (stage boundary)
   +- *(1) HashAggregate(keys=[department], functions=[partial_avg(salary)])
      +- *(1) Filter (salary > 50000)              ← Filter pushed down
         +- *(1) Scan ExistingRDD[id, department, salary]  ← Only 3 columns read
</code></pre>
<p>Key things to notice:</p>
<ul>
<li><code>Exchange</code> = shuffle. This is the stage boundary.</li>
<li><code>Filter</code> is pushed below the aggregation — filter first, aggregate less data.</li>
<li><code>Scan</code> only reads <code>id</code>, <code>department</code>, <code>salary</code> — column pruning removed <code>city</code>.</li>
<li><code>partial_avg</code> in Stage 1 means Spark computes partial averages per partition before shuffling (combines data locally first to reduce shuffle size).</li>
</ul>
<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Assuming your query runs exactly as written.</strong> It doesn't. Catalyst rewrites it, often significantly. Use <code>explain()</code> to see what actually runs.</li>
<li><strong>Manually optimizing what Catalyst already handles.</strong> You don't need to manually reorder <code>filter</code> before <code>select</code> — Catalyst does predicate pushdown automatically. Focus your optimization effort on things Catalyst can't fix: choosing the right join type, partitioning your data well, and avoiding UDFs.</li>
<li><strong>Using UDFs for logic that built-in functions can handle.</strong> Every UDF is a black box to Catalyst. <code>col("salary") > 50000</code> gets pushed down to the data source. <code>is_high_salary_udf(col("salary"))</code> cannot be.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>Catalyst transforms your logical query into an optimized physical plan through four phases.</li>
<li>Key optimizations: predicate pushdown (filter early), column pruning (read less), join reordering (join smart), constant folding (compute once).</li>
<li>UDFs break Catalyst because it can't see inside them — this is a bigger performance hit than the JVM-to-Python overhead alone.</li>
<li>Use <code>explain(True)</code> to see all four optimization phases; use <code>explain()</code> for just the physical plan.</li>
<li>Read physical plans from bottom to top. Look for <code>Exchange</code> (shuffles) and verify filters are pushed close to the scan.</li>
<li>Don't manually micro-optimize what Catalyst already handles — focus on the things it can't fix.</li>
</ul>
