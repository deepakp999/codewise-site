<h3 id="1-what-is-pyspark-and-how-does-it-differ-from-pandas">1. What is PySpark and how does it differ from pandas?</h3>
<p>PySpark is the Python API for Apache Spark, a distributed computing framework. The key difference: pandas processes data on a single machine's memory, while PySpark distributes data across a cluster of machines.</p>
<p>PySpark DataFrames are immutable and lazily evaluated. Pandas DataFrames are mutable and execute immediately. Use pandas for data under 10 GB, PySpark when data exceeds single-machine memory.</p>
<p><em>Covered in: Lesson 1 (What is Spark) and Lesson 2 (Spark vs Pandas)</em></p>
<h3 id="2-what-is-a-sparksession">2. What is a SparkSession?</h3>
<p>SparkSession is the entry point to all PySpark functionality. It manages the connection to the Spark cluster and provides methods to create DataFrames, run SQL queries, and configure Spark settings.</p>

<h3 id="3-what-is-the-difference-between-filter-and-where">3. What is the difference between <code>filter()</code> and <code>where()</code>?</h3>
<p>There is no difference. <code>where()</code> is an alias for <code>filter()</code>. They produce identical execution plans. Use whichever reads more naturally for your team.</p>
<p><em>Covered in: Lesson 8 (Selecting, Filtering, and Sorting)</em></p>

<h2 id="intermediate-level">Intermediate Level</h2>
<h3 id="6-what-is-lazy-evaluation">6. What is lazy evaluation?</h3>
<p>Transformations (filter, select, join) are not executed immediately. Spark builds a DAG of operations and only executes when an action (show, count, write) is called. This allows the Catalyst optimizer to rearrange and optimize the entire chain before running anything.</p>
<p><em>Covered in: Lesson 18 (Lazy Evaluation and the DAG)</em></p>
<h3 id="7-what-is-the-difference-between-transformations-and-actions">7. What is the difference between transformations and actions?</h3>
<p>Transformations create a new DataFrame without executing (filter, select, groupBy, join). Actions trigger computation and return results (show, count, collect, write). Every action recomputes the entire chain unless the data is cached.</p>
<p><em>Covered in: Lesson 18 (Lazy Evaluation and the DAG)</em></p>
<h3 id="8-what-is-a-partition-in-spark">8. What is a partition in Spark?</h3>
<p>A partition is a chunk of data that Spark processes in parallel. One task processes one partition. Spark creates one partition per CPU core by default, or uses <code>spark.sql.shuffle.partitions</code> (default 200) after shuffle operations.</p>
<p>Optimal partition size: 100 MB – 1 GB of data per partition.</p>
<p><em>Covered in: Lesson 19 (Partitions)</em></p>
<h3 id="9-what-is-a-shuffle-and-why-is-it-expensive">9. What is a shuffle and why is it expensive?</h3>
<p>A shuffle occurs when data must move between partitions across machines — triggered by groupBy, join, orderBy, and distinct. It's expensive because it involves disk I/O (writing shuffle files), network transfer (sending data between nodes), and serialization/deserialization.</p>
<p><em>Covered in: Lesson 20 (Shuffles)</em></p>
<h3 id="10-what-is-the-difference-between-repartition-and-coalesce">10. What is the difference between <code>repartition()</code> and <code>coalesce()</code>?</h3>
<p><code>repartition(n)</code> triggers a full shuffle and creates exactly n evenly distributed partitions. Can increase or decrease. <code>coalesce(n)</code> avoids a shuffle by combining adjacent partitions. Can only decrease. May produce uneven partitions.</p>
<p>Use <code>coalesce</code> to reduce partition count, <code>repartition</code> to increase or when you need even distribution.</p>
<p><em>Covered in: Lesson 22 (Repartition vs Coalesce)</em></p>
<h3 id="11-what-is-a-broadcast-join">11. What is a broadcast join?</h3>
<p>A broadcast join copies a small table to every executor, eliminating the shuffle for the large table. Spark auto-broadcasts tables under 10 MB. Use <code>broadcast()</code> to force it for larger lookup tables.</p>

<p>Window functions compute values across a group of rows related to the current row, without collapsing the data. Used for rankings, running totals, and comparing each row to its group.</p>

<h2 id="advanced-level">Advanced Level</h2>
<h3 id="13-what-is-the-catalyst-optimizer">13. What is the Catalyst optimizer?</h3>
<p>Catalyst is Spark's query optimizer. It transforms your logical query plan into an optimized physical plan through predicate pushdown (filter early), column pruning (read only needed columns), join reordering, and constant folding. UDFs are opaque to Catalyst — it can't optimize through them.</p>
<p><em>Covered in: Lesson 21 (Catalyst Optimizer)</em></p>
<h3 id="14-why-are-python-udfs-slow">14. Why are Python UDFs slow?</h3>
<p>Python UDFs require serializing each row from JVM to Python, executing the Python function, and serializing the result back. This row-by-row serialization is 10-100x slower than built-in functions. UDFs also prevent Catalyst from optimizing (no predicate pushdown through UDFs).</p>
<p>Use Pandas UDFs (<code>@pandas_udf</code>) for 5-10x improvement over regular UDFs, or find a built-in function equivalent.</p>
<p><em>Covered in: Lesson 17 (UDFs)</em></p>
<h3 id="15-how-do-you-handle-data-skew">15. How do you handle data skew?</h3>
<p>Data skew means uneven partition sizes — one partition has far more data than others, becoming a bottleneck. Fixes: salting (add random values to the skewed key), two-stage aggregation, filtering hot keys for separate processing, and enabling Adaptive Query Execution.</p>
<p><em>Covered in: Lesson 26 (Data Skew)</em></p>
<h3 id="16-what-is-the-difference-between-cache-and-persist">16. What is the difference between <code>cache()</code> and <code>persist()</code>?</h3>
<p><code>cache()</code> is shorthand for <code>persist(StorageLevel.MEMORY_AND_DISK)</code>. <code>persist()</code> lets you choose a storage level: MEMORY_ONLY, MEMORY_AND_DISK, DISK_ONLY, or serialized variants. Cache DataFrames that are expensive to compute AND used multiple times.</p>
<p><em>Covered in: Lesson 24 (Caching and Persistence)</em></p>
<h3 id="17-explain-the-execution-hierarchy-job--stage--task">17. Explain the execution hierarchy: Job → Stage → Task.</h3>
<p>A <strong>Job</strong> is created for each action (show, count, write). A job is divided into <strong>Stages</strong> at shuffle boundaries. Each stage is divided into <strong>Tasks</strong> — one per partition. Tasks are the actual units of work that run on executor cores.</p>
<p><em>Covered in: Lesson 5 (Understanding the Spark UI)</em></p>
<h3 id="18-what-are-narrow-vs-wide-transformations">18. What are narrow vs wide transformations?</h3>
<p>Narrow transformations (filter, select, map) process each partition independently — no data movement. Wide transformations (groupBy, join, orderBy) require data from multiple partitions — triggering a shuffle. Every wide transformation creates a new stage boundary.</p>
<p><em>Covered in: Lesson 20 (Shuffles)</em></p>
<h3 id="19-how-would-you-optimize-a-slow-pyspark-job">19. How would you optimize a slow PySpark job?</h3>
<p>Systematic approach: (1) Check the Spark UI for shuffle sizes and skew, (2) Reduce shuffles by filtering early and selecting fewer columns before joins, (3) Use broadcast joins for small tables, (4) Tune <code>spark.sql.shuffle.partitions</code> for your data size, (5) Cache intermediate results used multiple times, (6) Fix data skew with salting, (7) Replace UDFs with built-in functions, (8) Use <code>explain()</code> to verify the optimizer is doing what you expect.</p>
<p><em>Covered across: Lessons 20, 21, 24, 25, 26</em></p>
