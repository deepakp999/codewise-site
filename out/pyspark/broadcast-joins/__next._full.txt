</div><h2 id="the-problem-shuffle-joins-are-expensive">The Problem: Shuffle Joins Are Expensive</h2>
<p>In Lesson 15, we joined orders (large) with customers (small). In Lesson 20, we learned that joins trigger shuffles — both tables get redistributed across the cluster by the join key.</p>
<p>But think about it: if the customers table has only 5,000 rows (a few MB), why shuffle 100 million order rows? It's like moving an entire library to find one book.</p>
<h2 id="the-solution-send-the-small-table-everywhere">The Solution: Send the Small Table Everywhere</h2>
<p>A broadcast join copies the small table to every executor. Then each executor can join its local partition of the large table with the complete small table — no shuffle needed.</p>
<pre><code>Regular join:
  Orders (100M rows) ──shuffle──┐
                                 ├── Join
  Customers (5K rows) ─shuffle──┘

Broadcast join:
  Orders (100M rows) ─── no shuffle ─── Join
  Customers (5K rows) ── copied to every executor
</code></pre>

<h2 id="when-to-use-broadcast-joins">When to Use Broadcast Joins</h2>
<p><strong>Use broadcast when:</strong></p>
<ul>
<li>One table is small enough to fit in executor memory (typically &#x3C; 100 MB)</li>
<li>The small table is a lookup/dimension table (products, countries, categories)</li>
<li>You're joining a large fact table with a small dimension table</li>
</ul>
<p><strong>Don't use broadcast when:</strong></p>
<ul>
<li>Both tables are large — broadcasting a 10 GB table to 100 executors means 1 TB of network transfer</li>
<li>The small table changes frequently — it's broadcast once per query</li>
<li>Memory is tight — each executor holds a full copy</li>
</ul>
<h2 id="verifying-broadcast-in-the-spark-ui">Verifying Broadcast in the Spark UI</h2>
<p>After running a broadcast join, check the Spark UI:</p>
<ol>
<li>Click on the job → the stage</li>
<li>Look at the task metrics</li>
<li><strong>Shuffle Read should be zero (or very small)</strong> — that's the proof the broadcast worked</li>
<li>You'll see a "broadcast" stage that's usually very fast (&#x3C; 1 second for small tables)</li>
</ol>

<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Broadcasting a table that's too large.</strong> If you <code>broadcast()</code> a 5 GB table, Spark sends 5 GB to every executor. With 50 executors, that's 250 GB of network transfer — worse than a shuffle. You'll also get out-of-memory errors on executors.</li>
<li><strong>Not checking if auto-broadcast kicked in.</strong> Before manually adding <code>broadcast()</code>, check <code>explain()</code> — Spark might already be broadcasting. Adding <code>broadcast()</code> to an already-auto-broadcast join is harmless but unnecessary.</li>
<li><strong>Forgetting that broadcast happens per query.</strong> If you run 100 queries that each broadcast the same lookup table, it's broadcast 100 times. For repeated use, cache the broadcast table first.</li>
<li><strong>Using broadcast with left/full outer joins incorrectly.</strong> In a left join, only the right side can be broadcast. <code>orders.join(broadcast(customers), how="left")</code> works. But <code>broadcast(orders).join(customers, how="left")</code> won't broadcast because the left side of a left join can't be broadcast.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>Broadcast joins copy a small table to every executor, eliminating the shuffle on the large table.</li>
<li>Spark auto-broadcasts tables under 10 MB. Use <code>broadcast()</code> to force it for larger tables or when Spark's size estimate is wrong.</li>
<li>Broadcast joins turn expensive shuffle joins into fast, local joins — the single biggest join optimization.</li>
<li>Only broadcast tables that fit in executor memory (typically &#x3C; 100 MB).</li>
<li>Check <code>explain()</code> for <code>BroadcastHashJoin</code> to verify the broadcast is happening.</li>
</ul>
