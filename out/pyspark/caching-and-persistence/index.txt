<h3 id="storage-levels-explained">Storage Levels Explained</h3>
<p><strong>MEMORY_AND_DISK (default)</strong> — Store in memory. If it doesn't fit, spill to disk. Best general-purpose option.</p>
<p><strong>MEMORY_ONLY</strong> — Store in memory only. If it doesn't fit, the partitions that overflow are recomputed each time. Use when you have plenty of memory.</p>
<p><strong>DISK_ONLY</strong> — Store on disk only. Slower than memory but uses no executor memory. Use for very large DataFrames you access occasionally.</p>
<p><strong>MEMORY_ONLY_SER / MEMORY_AND_DISK_SER</strong> — Store as serialized bytes. Uses less memory but requires CPU to deserialize on each read. Use when memory is tight.</p>
<p><strong>For most cases, the default (MEMORY_AND_DISK) is the right choice.</strong> Only change it if you have a specific memory constraint.</p>

<h2 id="monitoring-cache-in-the-spark-ui">Monitoring Cache in the Spark UI</h2>
<p>Open the Spark UI (localhost:4040) and click the <strong>Storage</strong> tab. You'll see:</p>
<ul>
<li>Which DataFrames are cached</li>
<li>How much memory and disk each uses</li>
<li>What fraction is cached (if it didn't fully fit in memory)</li>
</ul>
<p>If you see "Fraction Cached" below 100%, your data is too large for the available memory and some partitions are being recomputed.</p>

<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Caching everything "just in case."</strong> Each cached DataFrame consumes memory. Too much caching causes memory pressure, which triggers garbage collection pauses and spills. Only cache DataFrames that are genuinely reused.</li>
<li><strong>Forgetting that <code>cache()</code> is lazy.</strong> Calling <code>df.cache()</code> doesn't compute anything — it just marks the DataFrame for caching. The actual caching happens on the first action. If you want to force caching immediately, call <code>df.cache().count()</code>.</li>
<li><strong>Not calling <code>unpersist()</code>.</strong> Cached data stays in memory until you explicitly remove it or the SparkSession ends. In long-running applications, forgetting to unpersist can cause out-of-memory errors.</li>
<li><strong>Caching before a filter.</strong> Cache the filtered result, not the full dataset. <code>df.cache()</code> followed by <code>df.filter(...)</code> caches everything and then filters — wasting memory on rows you don't need.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>Cache DataFrames that are expensive to compute AND used multiple times.</li>
<li><code>cache()</code> = <code>persist(MEMORY_AND_DISK)</code> — the default is usually fine.</li>
<li>Caching is lazy — the first action after <code>cache()</code> computes and stores the data.</li>
<li>Always <code>unpersist()</code> when done to free executor memory.</li>
<li>Don't cache everything — over-caching causes memory pressure.</li>
<li>Monitor cached data in the Spark UI's Storage tab.</li>
</ul>
