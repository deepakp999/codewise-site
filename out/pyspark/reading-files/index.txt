1b:T9c14,<h1 id="reading-csv-json-and-parquet-files">Reading CSV, JSON, and Parquet Files</h1>
<div data-cw-section="learn-box"><h2 id="what-youll-learn">What You'll Learn</h2>
<ul>
<li>How to read CSV files with various options (delimiters, encoding, malformed rows)</li>
<li>How to read JSON and JSON Lines files</li>
<li>Why Parquet is the preferred format for data engineers</li>
<li>How to write data back out in each format</li>
<li>How to read partitioned data from directories</li>
</ul>
</div><h2 id="the-three-formats-youll-use">The Three Formats You'll Use</h2>
<p>In data engineering, you'll encounter three file formats constantly:</p>
<ul>
<li><strong>CSV</strong> — human-readable, universal, but slow and error-prone at scale</li>
<li><strong>JSON</strong> — flexible structure, common from APIs, but verbose and slow to parse</li>
<li><strong>Parquet</strong> — binary, columnar, compressed, fast. The production standard.</li>
</ul>
<p>Think of it this way: CSV is a letter, JSON is an email, and Parquet is a database export. You use all three, but for serious work, you want Parquet.</p>

<ul>
<li><code>sep</code> — delimiter character. Use <code>"\t"</code> for tab-separated, <code>"|"</code> for pipe-separated</li>
<li><code>nullValue</code> — what string represents null. Many files use "NA", "NULL", "None", or empty strings</li>
<li><code>mode</code> — how to handle malformed rows: <code>PERMISSIVE</code> (default, keeps bad rows), <code>DROPMALFORMED</code> (drops them), <code>FAILFAST</code> (throws error)</li>
<li><code>dateFormat</code> — how dates are formatted in the file</li>
</ul>

<h2 id="reading-parquet-files">Reading Parquet Files</h2>
<h3 id="why-parquet">Why Parquet?</h3>
<p>Parquet is a columnar format — instead of storing data row by row, it stores data column by column. This matters for three reasons:</p>
<ol>
<li><strong>Speed</strong> — If you query 3 columns out of 50, Parquet only reads those 3 columns. CSV reads all 50.</li>
<li><strong>Compression</strong> — Similar values in a column compress better than mixed values in a row. Parquet files are typically 5-10x smaller than equivalent CSVs.</li>
<li><strong>Schema embedded</strong> — No <code>inferSchema</code> needed. The data types are stored in the file itself.</li>
</ol>
<h3 id="reading-parquet">Reading Parquet</h3>
<pre class="shiki shiki-themes github-light one-dark-pro" style="--shiki-light:#24292e;--shiki-dark:#abb2bf;--shiki-light-bg:#fff;--shiki-dark-bg:#282c34" tabindex="0"><code><span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic"># No options needed — schema is embedded in the file</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">df </span><span style="--shiki-light:#D73A49;--shiki-dark:#56B6C2">=</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> spark.read.</span><span style="--shiki-light:#24292E;--shiki-dark:#61AFEF">parquet</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">(</span><span style="--shiki-light:#032F62;--shiki-dark:#98C379">"data/sales.parquet"</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">)</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">df.</span><span style="--shiki-light:#24292E;--shiki-dark:#61AFEF">show</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">(</span><span style="--shiki-light:#005CC5;--shiki-dark:#D19A66">3</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">)</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">df.</span><span style="--shiki-light:#24292E;--shiki-dark:#61AFEF">printSchema</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">()</span></span></code></pre>
<p>That's it. No <code>header</code>, no <code>inferSchema</code>, no <code>sep</code>. Parquet just works.</p>
<h3 id="reading-partitioned-parquet">Reading partitioned Parquet</h3>
<p>Production data is often stored in partitioned directories:</p>
<pre><code>data/sales/
├── year=2023/
│   ├── month=01/
│   │   └── part-00000.parquet
│   ├── month=02/
│   │   └── part-00000.parquet
├── year=2024/
│   ├── month=01/
│   │   └── part-00000.parquet
</code></pre>
<pre class="shiki shiki-themes github-light one-dark-pro" style="--shiki-light:#24292e;--shiki-dark:#abb2bf;--shiki-light-bg:#fff;--shiki-dark-bg:#282c34" tabindex="0"><code><span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic"># Spark automatically discovers partitions</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">df </span><span style="--shiki-light:#D73A49;--shiki-dark:#56B6C2">=</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> spark.read.</span><span style="--shiki-light:#24292E;--shiki-dark:#61AFEF">parquet</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">(</span><span style="--shiki-light:#032F62;--shiki-dark:#98C379">"data/sales/"</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">)</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">df.</span><span style="--shiki-light:#24292E;--shiki-dark:#61AFEF">printSchema</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">()</span></span></code></pre>
<div data-cw-section="output-block"><h3 id="expected-output-1">Expected Output</h3>
<pre data-cw-output="true"><code>root

<p>Spark adds <code>year</code> and <code>month</code> as columns automatically. When you filter on partition columns, Spark only reads the relevant directories — it doesn't scan the entire dataset. This is called <strong>partition pruning</strong> and it's a major performance optimization.</p>

<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">df_2024 </span><span style="--shiki-light:#D73A49;--shiki-dark:#56B6C2">=</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> df.</span><span style="--shiki-light:#24292E;--shiki-dark:#61AFEF">filter</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">(</span><span style="--shiki-light:#24292E;--shiki-dark:#61AFEF">col</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">(</span><span style="--shiki-light:#032F62;--shiki-dark:#98C379">"year"</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">) </span><span style="--shiki-light:#D73A49;--shiki-dark:#56B6C2">==</span><span style="--shiki-light:#005CC5;--shiki-dark:#D19A66"> 2024</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">)</span></span></code></pre>

<h2 id="format-comparison">Format Comparison</h2>
<pre><code>Feature          CSV           JSON          Parquet
─────────────    ──────────    ──────────    ──────────
Human readable   Yes           Yes           No
Schema embedded  No            Partial       Yes
Compression      None          None          Excellent
Column pruning   No            No            Yes
Nested data      No            Yes           Yes
Read speed       Slow          Slow          Fast
File size        Large         Largest       Smallest
Production use   Import/export API data      Data lakes
</code></pre>
<p><strong>Rule of thumb:</strong> Read CSV/JSON when you receive data from external sources. Convert to Parquet immediately. Do all processing on Parquet. Only write CSV/JSON when an external system requires it.</p>
<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Writing CSV for internal use.</strong> If both the producer and consumer are PySpark, use Parquet. CSV loses type information, has no compression, and can't do column pruning. The only reason to write CSV is for non-Spark consumers (Excel, humans, legacy systems).</li>
<li><strong>Forgetting <code>multiLine=true</code> for standard JSON.</strong> PySpark expects one JSON object per line by default. A file with <code>[{...}, {...}]</code> will fail silently or produce garbage without this option.</li>
<li><strong>Not partitioning large datasets.</strong> If you write 100 GB of sales data as a single Parquet directory and later need "just January 2024," Spark reads all 100 GB. Partitioning by year/month means Spark reads only the ~4 GB it needs.</li>
<li><strong>Using <code>inferSchema</code> in production.</strong> We covered this in Lesson 7, but it bears repeating: define your schema explicitly. On a CSV with billions of rows, <code>inferSchema</code> doubles your read time.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>CSV is for import/export, JSON for API data, Parquet for everything else.</li>
<li>Parquet is columnar, compressed, and self-describing — use it as your default storage format.</li>
<li>Partitioned data lets Spark skip irrelevant files (partition pruning) — partition by columns you frequently filter on.</li>
<li>Read multiple files with directory paths or glob patterns.</li>
<li>Always define explicit schemas for CSV and JSON in production.</li>
<li>Write modes control what happens when data already exists: <code>overwrite</code>, <code>append</code>, <code>ignore</code>, <code>error</code>.</li>
</ul>
