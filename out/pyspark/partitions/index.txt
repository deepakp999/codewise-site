</div><h2 id="the-deck-of-cards-analogy">The Deck of Cards Analogy</h2>
<p>In Lesson 1, we introduced the vocabulary word "partition" — a chunk of your data. Now let's understand it properly.</p>
<p>Imagine you have a deck of 52 cards and 4 friends to help sort them. You deal 13 cards to each friend — that's 4 partitions of 13 cards each. Each friend sorts their pile simultaneously. More friends = more parallelism = faster sorting (up to a point).</p>
<p>Spark works the same way. It splits your DataFrame into partitions and processes each partition on a separate CPU core in parallel.</p>

<h2 id="how-spark-decides-partition-count">How Spark Decides Partition Count</h2>
<p>The default depends on how the data was created:</p>
<p><strong>From <code>createDataFrame</code> or <code>parallelize</code>:</strong> Spark uses the number of available CPU cores (typically <code>spark.default.parallelism</code>).</p>
<p><strong>From reading files:</strong> Spark creates roughly one partition per file block. For a 1 GB CSV with 128 MB HDFS block size, that's about 8 partitions. For a directory of 100 Parquet files, that's 100 partitions.</p>
<p><strong>After a shuffle operation (groupBy, join, orderBy):</strong> Spark uses <code>spark.sql.shuffle.partitions</code>, which defaults to <strong>200</strong>. This is often too many for small datasets and too few for very large ones.</p>
<pre class="shiki shiki-themes github-light one-dark-pro" style="--shiki-light:#24292e;--shiki-dark:#abb2bf;--shiki-light-bg:#fff;--shiki-dark-bg:#282c34" tabindex="0"><code><span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic"># Check the default shuffle partition count</span></span>

<h2 id="the-partitions--tasks--cores-relationship">The Partitions → Tasks → Cores Relationship</h2>
<pre><code>DataFrame has 8 partitions
    → Spark creates 8 tasks (one per partition)
        → 8 tasks run on available CPU cores in parallel
</code></pre>
<p>If you have 4 cores and 8 partitions, Spark runs 4 tasks at a time, then the other 4. If you have 4 cores and 200 partitions, Spark runs tasks in 50 waves of 4 — lots of overhead from task scheduling.</p>
<p><strong>The sweet spot:</strong> 2-4 partitions per core, with each partition containing 100 MB – 1 GB of data.</p>
<h2 id="too-few-partitions">Too Few Partitions</h2>
<pre class="shiki shiki-themes github-light one-dark-pro" style="--shiki-light:#24292e;--shiki-dark:#abb2bf;--shiki-light-bg:#fff;--shiki-dark-bg:#282c34" tabindex="0"><code><span class="line"><span style="--shiki-light:#6A737D;--shiki-light-font-style:inherit;--shiki-dark:#7F848E;--shiki-dark-font-style:italic"># Simulate too few partitions</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">df_one_partition </span><span style="--shiki-light:#D73A49;--shiki-dark:#56B6C2">=</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF"> df.</span><span style="--shiki-light:#24292E;--shiki-dark:#61AFEF">coalesce</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">(</span><span style="--shiki-light:#005CC5;--shiki-dark:#D19A66">1</span><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">)</span></span>

<p>With 1 partition, only 1 core does any work. The other cores sit idle. On a cluster with 100 cores, you're using 1% of your capacity.</p>
<p><strong>Signs of too few partitions:</strong></p>
<ul>
<li>Spark UI shows most executors are idle</li>
<li>One task takes much longer than others</li>
<li>You're not utilizing available cluster resources</li>
</ul>

<p>With 1000 partitions for 1000 rows, each partition has just 1 row. The overhead of managing 1000 tasks far exceeds the work in each task.</p>
<p><strong>Signs of too many partitions:</strong></p>
<ul>
<li>Tasks complete in milliseconds (less than 100ms)</li>
<li>The Spark UI shows a lot of task scheduling overhead</li>
<li>The overall job takes longer than expected despite low per-task time</li>
</ul>

<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Leaving <code>spark.sql.shuffle.partitions</code> at the default 200 for small datasets.</strong> If your data is a few MB, 200 partitions means each partition has kilobytes of data — pure overhead. Set it to 2-10 for small datasets.</li>
<li><strong>Using <code>repartition</code> when <code>coalesce</code> would work.</strong> Repartition triggers a full shuffle (moving data across the cluster). If you just want fewer partitions, <code>coalesce</code> avoids the shuffle by combining adjacent partitions.</li>
<li><strong>Ignoring partition count in the Spark UI.</strong> The Tasks column in the Spark UI shows you exactly how many partitions each stage processed. If you see 200 tasks completing in 5ms each, your partition count is too high.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>Partitions are chunks of data that Spark processes in parallel — one task per partition.</li>
<li>Default partition count depends on the data source and operation type.</li>
<li>After shuffle operations, Spark uses <code>spark.sql.shuffle.partitions</code> (default 200) — tune this for your data size.</li>
<li>Aim for 2-4 partitions per core, with 100 MB – 1 GB per partition.</li>
<li>Use <code>rdd.getNumPartitions()</code> and <code>spark_partition_id()</code> to inspect partitions.</li>
<li>Too few partitions = wasted cores. Too many = scheduling overhead. Both are bad.</li>
</ul>
