</div><h2 id="why-sql-in-pyspark">Why SQL in PySpark?</h2>
<p>You already know the DataFrame API — <code>df.select()</code>, <code>df.filter()</code>, <code>df.groupBy()</code>. So why learn SQL too?</p>
<p>Two practical reasons. First, most data teams have analysts who know SQL but not Python. If you expose your DataFrames as SQL tables, they can query them directly. Second, some operations are simply easier to express in SQL — complex joins, subqueries, and CASE statements often read more naturally in SQL than in chained DataFrame calls.</p>
<p>The good news: PySpark's SQL engine uses the exact same optimizer (Catalyst) as the DataFrame API. There's no performance difference. Choose whichever is clearer for the task.</p>

<p><strong>Use SQL when:</strong> the query involves complex joins, subqueries, CASE statements, or when your team thinks in SQL.</p>
<p><strong>Use DataFrame API when:</strong> you're building a pipeline with many chained transformations, or when you need programmatic column construction (like looping over column names).</p>
<p><strong>Use both when:</strong> that's what most real codebases do.</p>
<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Forgetting to create the view first.</strong> <code>spark.sql("SELECT * FROM employees")</code> will fail with "Table or view not found" if you haven't called <code>createOrReplaceTempView("employees")</code>. The view registration step is easy to forget.</li>
<li><strong>Using double quotes for SQL strings.</strong> SQL string literals use single quotes: <code>WHERE name = 'Alice'</code>, not <code>WHERE name = "Alice"</code>. Double quotes in SQL are for column/table names with special characters.</li>
<li><strong>Assuming SQL views persist between sessions.</strong> Temp views exist only within the current SparkSession. If you restart Spark, all views are gone. We'll cover persistent views in the next lesson.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li><code>createOrReplaceTempView("name")</code> registers a DataFrame as a SQL table.</li>
<li><code>spark.sql("...")</code> runs SQL and returns a DataFrame — no performance difference from the DataFrame API.</li>
<li>SQL and DataFrame API use the same Catalyst optimizer — choose whichever reads more clearly.</li>
<li>The result of <code>spark.sql()</code> is a normal DataFrame that you can chain further operations on.</li>
<li>Most real codebases mix both SQL and DataFrame API freely.</li>
</ul>
