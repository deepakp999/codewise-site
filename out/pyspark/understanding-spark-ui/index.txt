<h2 id="the-main-tabs">The Main Tabs</h2>
<p>The Spark UI has several tabs. Here are the most important ones:</p>
<h3 id="jobs-tab">Jobs Tab</h3>
<p>Shows all jobs triggered by actions (<code>.show()</code>, <code>.count()</code>, <code>.write()</code>). Each job has:</p>
<ul>
<li><strong>Status</strong>: Running, Succeeded, or Failed</li>
<li><strong>Duration</strong>: Total execution time</li>
<li><strong>Stages</strong>: How many stages the job was split into</li>
</ul>
<h3 id="stages-tab">Stages Tab</h3>
<p>Each job is split into stages at <strong>shuffle boundaries</strong>. A stage contains tasks that can run in parallel:</p>
<pre class="shiki shiki-themes github-light one-dark-pro" style="--shiki-light:#24292e;--shiki-dark:#abb2bf;--shiki-light-bg:#fff;--shiki-dark-bg:#282c34" tabindex="0"><code><span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">graph LR</span></span>

<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">    A --> C[Stage 2: Shuffle]</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">    A --> D[Stage 3: Aggregate]</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">    B --> E[Task 1.1]</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">    B --> F[Task 1.2]</span></span>

<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#ABB2BF">    D --> I[Task 3.2]</span></span></code></pre>
<h3 id="storage-tab">Storage Tab</h3>
<p>Shows cached/persisted DataFrames and their memory usage.</p>
<h3 id="sqldataframe-tab">SQL/DataFrame Tab</h3>
<p>Shows the execution plans for SQL queries and DataFrame operations — essential for optimization.</p>
<h2 id="jobs-stages-and-tasks-explained">Jobs, Stages, and Tasks Explained</h2>
<p>Understanding this hierarchy is crucial:</p>
<table>
<thead>
<tr>
<th>Level</th>
<th>What It Is</th>
<th>Triggered By</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Job</strong></td>
<td>A complete computation</td>
<td>An action (<code>.show()</code>, <code>.count()</code>, <code>.write()</code>)</td>
</tr>
<tr>
<td><strong>Stage</strong></td>
<td>A set of tasks with no shuffles between them</td>
<td>Shuffle boundaries (<code>.groupBy()</code>, <code>.join()</code>)</td>

<tr>
<td><strong>Task</strong></td>
<td>Work done on one data partition</td>
<td>One task per partition per stage</td>
</tr>
</tbody>
</table>

<h2 id="reading-the-dag-visualization">Reading the DAG Visualization</h2>
<p>Click on any job to see its <strong>Directed Acyclic Graph (DAG)</strong>. This shows the physical execution plan:</p>
<ul>
<li><strong>Green boxes</strong>: Completed stages</li>
<li><strong>Blue boxes</strong>: Skipped stages (data was cached)</li>
<li><strong>Arrows</strong>: Data flow between stages</li>
</ul>
<p>The DAG reveals where shuffles happen. Each shuffle boundary means data is being redistributed across partitions — an expensive operation.</p>
<h2 id="key-metrics-to-watch">Key Metrics to Watch</h2>
<h3 id="in-the-stages-tab-look-for">In the Stages tab, look for:</h3>
<ol>
<li><strong>Shuffle Read/Write Size</strong>: Large shuffles slow things down</li>
<li><strong>Task Duration</strong>: If some tasks are much slower than others, you have a <strong>data skew</strong> problem</li>
<li><strong>GC Time</strong>: High garbage collection time means you need more memory</li>
<li><strong>Input Size</strong>: Verify Spark is reading the expected amount of data</li>
</ol>
<h3 id="task-duration-distribution">Task Duration Distribution</h3>
<p>The <strong>Event Timeline</strong> in the stage detail page shows task execution over time. Ideally, all tasks should finish around the same time. If one task takes 10x longer, that partition has more data than others.</p>
<h2 id="using-the-sql-tab">Using the SQL Tab</h2>
<p>For DataFrame operations, the SQL tab is gold. It shows:</p>
<ul>
<li>The <strong>logical plan</strong> (what you asked for)</li>
<li>The <strong>physical plan</strong> (how Spark will do it)</li>
<li><strong>Metrics</strong> per operator (rows processed, time spent)</li>
</ul>

<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Ignoring the Spark UI completely.</strong> The UI tells you exactly where time is spent. If your job is slow, the answer is in the UI — not in guessing.</li>
<li><strong>Not checking for data skew.</strong> If one task takes 10 minutes and the rest take 10 seconds, one partition has most of the data. The Stages tab reveals this instantly.</li>
<li><strong>Forgetting the UI disappears when SparkSession stops.</strong> The UI is only available while Spark is running. For historical data, configure the Spark History Server.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>The Spark UI runs at <code>localhost:4040</code> automatically</li>
<li>Jobs → Stages → Tasks is the execution hierarchy</li>
<li>Shuffles create stage boundaries — minimize them for performance</li>
<li>The SQL tab shows execution plans and per-operator metrics</li>
<li>Watch for data skew by comparing task durations</li>
<li>The UI is your best friend for debugging slow jobs</li>
</ul>
