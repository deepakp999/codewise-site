</div><h2 id="what-is-data-skew">What Is Data Skew?</h2>
<p>Data skew means your data is unevenly distributed across partitions. Instead of every partition having roughly the same amount of data, one or two partitions have vastly more than the others.</p>
<p>Imagine 4 friends sorting cards again. But this time, one friend gets 48 cards and the other three get 1 card each. Three friends finish instantly. Everyone waits for the one friend struggling through 48 cards. Your job is only as fast as the slowest partition.</p>

<p>90% of the data is in one group. When you do a <code>groupBy("department")</code>, one partition processes 90,000 rows while others process 5,000. The job takes as long as the slowest partition.</p>
<h2 id="detecting-skew">Detecting Skew</h2>
<h3 id="in-the-spark-ui">In the Spark UI</h3>
<p>After running a <code>groupBy</code> or <code>join</code>, look at the stage details:</p>
<ol>
<li>Click on the stage → Summary Metrics</li>
<li>Compare <strong>Max</strong> task duration to <strong>Median</strong> task duration</li>
<li>If Max is 10x or more than Median, you have skew</li>
<li>Look at <strong>Shuffle Read Size</strong> per task — the skewed task reads much more data</li>
</ol>

<p>AQE detects skewed partitions during execution and splits them into smaller sub-partitions. It's not a complete solution for all skew problems, but it handles moderate skew automatically.</p>
<h2 id="real-world-skew-scenarios">Real-World Skew Scenarios</h2>
<p><strong>Null keys:</strong> If 30% of your join key is null, all null rows go to one partition. Fix: filter nulls before the join, process them separately.</p>
<p><strong>Popular users:</strong> In social media data, celebrity accounts have millions of followers while average users have hundreds. Any join or groupBy on user_id will be skewed. Fix: salting.</p>
<p><strong>Default values:</strong> A "department" column where 60% of rows have "Unknown" as the department. Fix: filter out "Unknown" rows, process them separately, union the results.</p>
<p><strong>Time-based data:</strong> All orders on Black Friday go to one day's partition while other days have 1/10th the volume. Fix: partition by hour instead of day.</p>
<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Not diagnosing skew before trying to fix it.</strong> Always confirm skew exists by checking the Spark UI task metrics or value distribution. Many slow jobs are caused by insufficient memory or bad join strategies, not skew.</li>
<li><strong>Using too many salt values.</strong> Salting with 100 values on a products table with 10,000 rows creates 1,000,000 rows in the exploded table. Use the minimum salt factor needed — start with 5-10.</li>
<li><strong>Assuming AQE fixes all skew.</strong> AQE handles moderate skew in sort-merge joins. It doesn't help with groupBy skew or broadcast joins. For severe skew, manual salting is still necessary.</li>
<li><strong>Ignoring null key skew.</strong> Null values in join keys all hash to the same partition. Always filter or handle nulls before joining.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>Data skew = uneven partition sizes. Your job is only as fast as the slowest partition.</li>
<li>Detect skew in the Spark UI (compare max vs median task duration) or by checking value distributions.</li>
<li>Salting is the primary fix for skewed joins — add randomness to spread the hot key across partitions.</li>
<li>Two-stage aggregation fixes skewed groupBy operations.</li>
<li>AQE can auto-handle moderate skew but isn't a complete solution.</li>
<li>Common skew sources: null keys, popular entities, default values, time-based hotspots.</li>
</ul>
