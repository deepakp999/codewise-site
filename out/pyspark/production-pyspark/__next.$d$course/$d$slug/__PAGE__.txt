<div data-cw-section="learn-box"><h2 id="what-youll-learn">What You'll Learn</h2>
<ul>
<li>How to structure a PySpark application for production</li>
<li>How to use <code>spark-submit</code> to run jobs on a cluster</li>
<li>Configuration management patterns</li>
<li>Logging and error handling</li>
<li>How to write testable PySpark code</li>
</ul>
</div><h2 id="from-notebook-to-production">From Notebook to Production</h2>
<p>Everything in this course so far has been interactive — you write code, run it, see results. Production PySpark is different:</p>
<ul>
<li>It runs on a schedule (daily, hourly)</li>
<li>It runs on a cluster, not your laptop</li>
<li>Nobody is watching it — it needs to log what happened</li>
<li>It needs to handle failures gracefully</li>
<li>It needs to be testable and maintainable</li>
</ul>

<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Putting everything in one giant script.</strong> Separate extract, transform, and load into functions. This makes the code testable, readable, and reusable.</li>
<li><strong>Not logging enough.</strong> In production, you can't add print statements and re-run. Log row counts after each stage, warn on data quality issues, and error on failures. Future you will thank present you.</li>
<li><strong>Using <code>client</code> deploy mode in production.</strong> In client mode, the driver runs on the machine that submits the job. If that machine goes down, the job fails. Use <code>cluster</code> mode so the driver runs on the cluster.</li>
<li><strong>Not validating input data.</strong> If yesterday's data didn't arrive and your pipeline reads zero rows, it should fail loudly — not silently produce empty output that breaks downstream systems.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>Production PySpark has a clear structure: Config → SparkSession → Extract → Transform → Load → Error handling.</li>
<li>Use <code>spark-submit</code> to run on clusters — configure executors, memory, and cores via command-line options.</li>
<li>Separate transformation logic from I/O for testability.</li>
<li>Log everything: row counts, data quality warnings, errors with stack traces.</li>
<li>Validate inputs early — fail fast on bad data rather than producing bad output.</li>
<li>Use configuration objects instead of hardcoded paths and settings.</li>
</ul>
