<h2 id="why-udfs-are-slow">Why UDFs Are Slow</h2>
<p>This is the most important section of this lesson. UDFs have a serious performance cost.</p>
<p>When you use a built-in function like <code>upper()</code>, Spark runs it inside its optimized JVM engine. When you use a Python UDF, here's what actually happens for every single row:</p>
<ol>
<li>Spark serializes the row data from JVM format to Python format</li>
<li>The data is sent to a Python worker process</li>
<li>Your Python function runs on that one row</li>
<li>The result is serialized back from Python to JVM format</li>
<li>Spark receives the result and continues</li>
</ol>
<p>This serialize → send → execute → send back cycle happens <strong>for every row</strong>. On a million rows, that's a million round trips between JVM and Python. Built-in functions skip all of this — they run entirely inside the JVM.</p>
<p><strong>Typical performance difference:</strong> A UDF can be 10-100x slower than the equivalent built-in function.</p>

<h2 id="when-you-actually-need-a-udf">When You Actually Need a UDF</h2>
<p>Sometimes there's no built-in alternative:</p>
<ul>
<li><strong>Complex business logic</strong> that can't be expressed with <code>when/otherwise</code> chains</li>
<li><strong>External library calls</strong> (e.g., using a regex library, geocoding, NLP tokenization)</li>
<li><strong>Data validation</strong> with rules that are too complex for SQL expressions</li>
<li><strong>Legacy code</strong> that must stay in Python</li>
</ul>
<p>Even then, consider these faster alternatives first:</p>
<h3 id="pandas-udfs-vectorized--5-10x-faster-than-regular-udfs">Pandas UDFs (Vectorized) — 5-10x faster than regular UDFs</h3>

<p>Pandas UDFs process data in batches (as pandas Series) instead of row by row. They use Apache Arrow for efficient data transfer between JVM and Python. They're 5-10x faster than regular UDFs for most operations.</p>
<div data-cw-section="mistake-card"><h2 id="common-mistakes">Common Mistakes</h2>
<ul>
<li><strong>Using UDFs when built-in functions exist.</strong> Always check the PySpark functions documentation first. There are 300+ built-in functions covering strings, math, dates, arrays, maps, and more. A 5-minute search can save you a 10x performance penalty.</li>
<li><strong>Forgetting to specify the return type.</strong> <code>udf(my_func)</code> without a return type defaults to <code>StringType()</code>. If your function returns an integer, you'll get strings. Always specify: <code>udf(my_func, IntegerType())</code>.</li>
<li><strong>Not handling nulls in UDFs.</strong> If your column has null values and your Python function doesn't check for None, you'll get <code>TypeError</code> exceptions. Always start your UDF with a null check.</li>
<li><strong>Using regular UDFs when Pandas UDFs would work.</strong> If your logic can operate on a pandas Series (most string/math operations can), use <code>@pandas_udf</code> for significantly better performance.</li>
</ul>
</div><h2 id="key-takeaways">Key Takeaways</h2>
<ul>
<li>UDFs are 10-100x slower than built-in functions because of JVM ↔ Python serialization overhead.</li>
<li>Always try to solve the problem with built-in functions (<code>when/otherwise</code>, <code>split</code>, <code>regexp_replace</code>, etc.) before writing a UDF.</li>
<li>If you must write a UDF, use Pandas UDFs (<code>@pandas_udf</code>) for 5-10x better performance over regular UDFs.</li>
<li>Always specify the return type and handle null values in your UDF.</li>
<li>Register UDFs with <code>spark.udf.register()</code> to use them in SQL queries.</li>
<li>In Lesson 21 (Catalyst Optimizer), we'll see why UDFs break Spark's query optimization — another reason to avoid them.</li>
</ul>
